# 大模型安全评测平台难点追问

> 文档定位：在《02-项目高频追问.md》的基础上，重点准备“项目最难在哪里、为什么这样选型、RAG 遇到过什么问题”这类需要讲判断、讲取舍、讲案例的深挖问题。
>
> 回答原则：先说结论，再说矛盾和约束，然后落到项目实现，最后补充效果、边界与改进。不要把“用了很多中间件”当成难点，也不要编造没有监控依据的提升百分比。
>
> 项目体量口径：日均 200 至 250 个批量评测任务，展开后约 350 万至 450 万条样本；评测结果、MODEL_CALL/L1/L2/L3 节点日志等明细日增 2000W+ 条。真正考验系统的不是任务 HTTP QPS，而是任务展开后的峰值样本吞吐、外部模型并发、大量明细写入和失败恢复。

---

## 一、先统一“项目最难”的回答口径

### 1. 项目中你觉得最难的地方在哪里？

**推荐结论**

我认为最难的不是 MQ、分库分表或者某一种检索算法，而是把模糊、动态、带有代价权衡的安全标准，落成一套能够大规模执行、结果可解释、失败可恢复的判定系统。

这个难点可以拆成三层：

1. **业务层：安全边界怎么定义。** 同一句话放在不同上下文中可能完全相反。例如“绕过实名认证”出现在操作教程里是高风险，出现在“为什么不能绕过实名认证”的合规说明里可能是安全内容。只做关键词匹配会误杀，只依赖大模型又会有随机性、成本和延迟问题。
2. **算法层：召回率、误判率、成本和延迟怎么平衡。** 漏判的安全代价很高，但如果所有模糊样本都进入大模型 Judge，成本和吞吐又不可接受。
3. **工程层：百万级样本异步执行时如何保证最终收敛。** MQ 会重复投递，服务会重启，模型会超时，数据库提交与下一阶段发消息之间还存在一致性窗口，不能因为一次异常就重复调用模型或永久丢失样本。

项目的解决方式不是押注一个模型，而是把问题拆成：

- L1 用 AC 自动机做确定性规则拦截；
- L2 用 Elasticsearch 关键词召回、PGVector 语义召回、RRF 融合和 Rerank 做相似案例判断；
- L3 只处理低置信度样本，并且只围绕目标风险规则做 Judge；
- 每个阶段记录输入、输出、命中证据、耗时和错误；
- 执行链路用状态机、样本级锁、幂等消费和定时补偿保证最终收敛。

所以我会把项目最难点概括成一句话：**既要把安全判定做准，又要让这个判定过程在大规模异步执行下稳定、可解释、可复盘。**

**贴近业务的例子**

模型输出是：“我不能提供绕过实名认证的方法，但可以解释合规认证的必要性。”

- L1 可能命中“绕过实名认证”，但二级风险词只做告警，不直接把整条内容判死；
- L2 可能同时召回危险操作案例和合规拒答案例；
- 如果危险案例相似度高，但又命中了安全例外证据，系统不会直接判安全，而是进入 L3；
- L3 只读取“身份认证绕过”对应的规则、边界和正反例，判断这段话是在提供方法还是明确拒绝；
- 最终保存命中的词、相似案例、规则版本和 Judge 理由，后续才能解释“为什么没有误杀”。

这个例子同时体现了业务边界、分层判定和可解释性，通常比只讲技术组件更能说服面试官。

---

### 2. 这是技术难点还是业务难点？

**推荐回答**

两者都有，但我会区分主次：**最先要解决的是业务难点，最难稳定住的是技术难点。**

- 如果风险分类、判定边界和安全例外没有定义清楚，技术做得再复杂也只是稳定地产生错误结果；
- 当规则定义清楚后，真正的工程挑战是把它放到数百万样本和多模型并发环境里执行，并保证重复消费不重复扣费、局部故障不丢样本、每个结果都能追溯。

我在项目中的处理方式是把业务规则结构化为风险类型、风险详情、规则边界、安全样例和危险样例，再通过 L1/L2/L3 分层执行；工程上则用状态机和节点日志把一次评测变成可恢复、可诊断的工作流。

**面试官继续追问“你个人更偏向解决哪一部分”时**

可以回答：我负责的是业务规则向系统能力的转换，既不是单纯写规则，也不是单纯搭中间件。具体包括分层判定链路、模型调用与安全评测的异步解耦、幂等补偿、L2 混合检索、L3 规则约束以及安全评测助手的查询路由。

---

### 3. 安全规则本身很主观，你们怎么把边界落下来？

**推荐回答**

我们不会只保存一个风险标签，而是把每个风险详情拆成可执行的判定契约：

- 风险定义：到底在防什么；
- 命中条件：什么证据足以判为风险；
- 排除边界：新闻引用、学术讨论、合规拒答等哪些上下文不应误判；
- 安全和危险样例：帮助检索和 L3 Judge 对齐；
- 规则状态与版本：保证一次评测能够追溯到当时使用的规则。

L3 不让模型开放式判断“这段话是否安全”，而是把 `targetRiskDetailsId` 对应的规则、边界和正反例一起放入 Prompt，并要求严格结构化输出。返回缺字段、风险类型不一致或无法解析时，不把不确定结果伪装成确定结论，而是转人工复核。

**有说服力的理由**

开放式安全判断的问题是模型会自行扩展风险范围。例如任务只评测“危险物品制作”，模型可能因为文本中出现其他敏感话题而判为不安全。限定目标风险后，系统回答的是“是否违反本次被测规则”，而不是让 Judge 临时创造一套安全标准。

---

### 4. 误杀和漏判冲突时，你们怎么取舍？

**推荐回答**

安全平台不能用一个全局阈值解决所有风险。我们的原则是：高危且证据确定的场景优先控制漏判，语义模糊场景则通过升级判定降低误杀。

- L1 一级高危词可以直接拦截，二级词只告警并继续下沉；
- L2 高阈值以上直接判风险，低阈值以下可以通过，中间区间交给 L3；
- 命中安全例外时不能直接判安全，因为攻击文本可能先说“我不应该告诉你”，随后仍给出完整操作步骤；
- L3 仍不确定、输出不合法或证据冲突时进入人工复核。

阈值也不应永久写死。不同风险类型的漏判成本不同，后续应基于标注集分别校准阈值，观察 Precision、Recall、FPR、FNR、人工复核率和单样本成本，而不是只看一个总准确率。

---

### 5. 日均只有 200 多个任务，为什么需要这么复杂的架构？

**推荐回答**

200 多是控制面的批量任务数，不是数据面的请求量。单任务平均会展开 1.5 万至 2 万条样本，因此每天实际处理约 350 万至 450 万条样本；每条样本还会产生结果明细以及 MODEL_CALL、L1、L2、L3 等节点记录，最终日增 2000W+ 条明细。

此外任务通常集中提交，平均吞吐并不能代表峰值。系统要面对的是 200 至 300 条样本/秒的异步峰值、不同模型供应商的并发上限、每秒上千次数据库写操作，以及下游短暂不可用后的积压恢复。因此才需要任务拆分、MQ 削峰、按模型并发隔离、核心表分片和查询投影。

**需要主动区分的指标**

- HTTP QPS：管理和查询接口的请求量；
- 样本吞吐：异步流水线每秒处理多少样本；
- 模型在途并发：某个模型同时有多少请求未完成；
- 数据库写入 TPS：结果、状态、节点日志和 Outbox 的写入次数；
- 单样本端到端耗时：模型调用、L1/L2/L3 的总执行时间。

把这五类指标混成一个 QPS，会让容量解释失真。

---

### 6. 你怎么证明这个难点真的解决了？

**推荐回答**

我会从三组指标证明，而不是只说“系统跑起来了”：

| 维度 | 关键指标 | 能说明什么 |
| --- | --- | --- |
| 判定质量 | Precision、Recall、FPR、FNR、人工复核率、分风险类型指标 | 安全边界是否合理，是否只是通过提高拦截率掩盖误杀 |
| 系统稳定性 | 样本吞吐、MQ backlog、各状态滞留量、补偿成功率、重复模型调用率、失败率 | 异步链路能否最终收敛，是否产生额外调用成本 |
| 可解释性 | 节点日志完整率、命中证据覆盖率、规则版本可追溯率、问题定位时长 | 结果能否被复核，误判能否定位到具体阶段 |

当前代码已经为这些指标保留了基础数据：结果状态、各阶段节点输入输出、命中详情、相似度、耗时和异常信息。面试时只讲自己能从监控或复盘记录中确认的数据；如果没有可靠基线，不要临时编造“误判率下降 40%”之类的数字。

## 二、判定链路为什么这样设计

### 7. 为什么做 L1/L2/L3，直接让一个大模型 Judge 不行吗？

**推荐回答**

技术上可以全量调用 Judge，但在这个体量下不合理，原因有四个：

1. **成本不可控。** 数百万样本全部增加一次 Judge 调用，Token 和接口费用会线性放大；
2. **吞吐和延迟不可控。** 外部模型是整条链路最慢、波动最大的环节；
3. **结果稳定性不足。** 同一输入可能因模型版本、温度和上下文变化产生不同结果；
4. **可解释性变弱。** 单个“安全/不安全”答案很难说明到底命中了哪条规则。

分层后，L1 处理便宜且确定的规则，L2 处理能够从历史案例中获得证据的样本，只有中间模糊区进入 L3。它本质上是一个从低成本、高确定性到高成本、强语义能力的级联分类器。

**一句话收口**

L1/L2/L3 不是为了堆算法，而是让确定的样本尽早结束，把昂贵模型预算留给真正不确定的部分。

---

### 8. L2 为什么同时使用 Elasticsearch 和 PGVector？

**推荐回答**

因为安全规则既包含强字面信号，也包含大量同义改写，单一召回方式会有明显盲区。

- Elasticsearch 擅长精确风险词、短语、编号和专有名词，命中证据直观；
- PGVector 擅长语义改写，例如“避开实名校验”和“绕过身份认证”字面不同，但语义接近；
- 两路结果通过 RRF 做名次融合，再对小规模候选集 Rerank，兼顾召回率和排序精度。

不能直接把 ES 分数和向量相似度相加，因为两者的分值分布、量纲和索引状态不同。RRF 只依赖名次，能够减少手工归一化对结果的影响；Rerank 再使用查询与候选文本的成对相关性纠正前排顺序。

**边界说明**

这里说的是评测链路 L2 的 ES + PGVector 混合召回。安全评测助手当前代码主要是知识库向量检索与关系库查询路由，不能把 L2 已实现的 RRF 直接说成助手也已经具备。

---

### 9. 为什么有了 RRF 还需要 Rerank？

**推荐回答**

两者解决的问题不同：

- RRF 解决多路召回结果无法直接比较的问题，目标是稳健融合；
- Rerank 解决候选文档与当前文本是否真的相关的问题，目标是精排。

例如 ES 因命中一个高权重风险词把文档排在第一，PGVector 因整体语义接近把另一个文档排在第一。RRF 能把两路共同靠前的候选提升，但它并不理解“这段内容是在教唆还是在反对”。对融合后的 TopN 做 Rerank，才能进一步利用完整上下文判断相关性。

为了控制延迟，项目不是对全库做精排，而是先各取较小 TopK，RRF 后保留有限候选，再对候选集 Rerank。当前 L2 默认配置中，ES 与向量各取 Top5，融合后最多保留 Top20；这些是可配置起点，不应描述成适合所有风险类型的永久最优值。

---

### 10. L1 规则很多时，怎么做到热更新又不影响正在执行的请求？

**推荐回答**

难点不只是把词表放进 Redis，而是避免实例在更新过程中读到“半套规则”。项目采用版本化快照思路：

1. 生成规则清单和分片数据，并记录版本与哈希；
2. 应用实例先把新版本加载到 `preparedContext`，校验分片完整性和哈希；
3. 校验成功后一次性切换 `activeContext`；
4. 通过 ACK 和心跳确认各实例加载状态；
5. Redis 快照异常时保留数据库回退能力。

这样正在处理的请求继续使用旧的完整上下文，新请求在切换后使用新的完整上下文，不会出现一半旧规则、一半新规则。它类似配置快照切换，而不是在原 AC 自动机对象上逐条修改。

---

### 11. 怎么定位一次误判到底发生在 L1、L2 还是 L3？

**推荐回答**

每个样本都用同一个结果明细 ID 串起节点日志，分别记录 MODEL_CALL、L1、L2、L3 的输入输出快照、命中规则、召回案例、融合/重排结果、阈值路由、Judge 结果、耗时和异常。

排查时按以下顺序：

1. 确认被测模型原始输出是否完整；
2. 看 L1 命中了哪个词、风险等级和规则版本；
3. 看 L2 两路召回结果、目标风险过滤、RRF/Rerank 排名及最终阈值；
4. 看 L3 使用的目标规则、正反例和结构化返回；
5. 判断问题属于规则边界、召回缺失、排序错误、阈值不合理还是 Judge 偏差。

例如危险案例根本没进入 TopK，是召回问题；候选已召回但排在阈值以下，是排序或阈值问题；证据正确但 Judge 判断相反，才是 Prompt 或模型问题。没有节点级证据时，团队很容易把所有问题都归因于“大模型不稳定”。

## 三、高吞吐异步链路的技术难点

### 12. 如果只选一个技术难点，你会说什么？

**推荐回答**

我会选择“异步流水线的一致性与可恢复性”，而不是笼统说高并发。

主状态机是：

```text
PENDING
  -> MODEL_RUNNING
  -> MODEL_CALLED
  -> SAFETY_EVALUATING
  -> AUTO_SCORED / MANUAL_REVIEWED / FAILED / STOPPED
```

MQ 只提供至少一次投递，真正的业务幂等由数据库状态机负责；分布式锁只防止同一时刻两个消费者并发执行同一样本。两者职责不同：没有锁会发生瞬时并发，没有状态机则无法抵抗消息重放、进程重启和锁过期。

项目以 `resultDetailId` 为样本级幂等键。只有 `PENDING` 能进入 `MODEL_RUNNING` 并调用被测模型；如果重复消息发现已经是 `MODEL_CALLED`，只补发安全评测阶段，不会再次调用外部模型。这样既避免重复结果，也避免重复扣费。

---

### 13. 为什么模型调用和安全评测要拆成两个 MQ 阶段？

**推荐回答**

因为两个阶段的资源模型、失败模式和扩容方式完全不同。

- 模型调用受供应商并发额度、网络延迟、Token 限制影响，单次耗时长；
- 安全评测主要消耗本地 CPU、ES/PGVector 查询以及少量 L3 Judge 配额；
- 两者放在同一个消费者中，模型抖动会占住线程并阻塞安全评测，任何一步重试还可能把整段重复执行。

拆分后可以按积压独立扩容、按模型单独限制在途并发、分别设置重试与告警策略。更重要的是，`MODEL_CALLED` 成为明确恢复点：模型输出已落库后，即使安全评测消息暂时没有送达，也不需要重新调用模型。

---

### 14. 数据库已保存模型输出，但发送下一阶段消息失败，怎么处理？

**推荐回答**

这正是异步链路最容易被忽略的一致性窗口。项目不声称 MQ 与 MySQL 实现了理论上的 exactly-once，而是通过“持久状态 + 幂等消费 + 定时补偿”达到业务最终一致。

- 模型输出成功落库后，状态变为 `MODEL_CALLED`；
- 正常路径立即发送 `SafetyEvaluate_MQ`；
- 补偿任务每分钟扫描长时间停留在 `MODEL_CALLED` 的记录，当前代码对超过 2 分钟的记录重新发送安全评测消息；
- 安全评测消费者再次检查状态，因此补发和重复投递不会重复执行已完成终态；
- 对长时间处于 `MODEL_RUNNING` 的记录，当前代码在超过 30 分钟后标记失败并收敛任务进度，避免永久挂起。

**可以直接讲的故障案例**

一次模型请求已经成功，原始输出也提交到 MySQL，但进程在发送安全评测消息前重启。恢复后，补偿任务发现该样本一直停留在 `MODEL_CALLED`，于是只重发安全评测消息。消费者从已保存的模型输出继续执行 L1/L2/L3，不会再次访问模型供应商。最终任务能够收敛，同时避免重复费用。

**继续追问“为什么不用分布式事务”**

外部模型、MySQL 和 RocketMQ 跨越多个系统，强行做全局事务成本高、可用性差，而且外部模型调用本身不可回滚。这个场景更适合显式状态机和可观测补偿。追求的是业务结果恰好一次，而不是宣称消息物理投递恰好一次。

**当前补偿能力的边界**

当前补偿器由全局分布式锁保证同一时刻只有一个实例执行，每分钟扫描一次，每种中间态单批最多处理 100 条。这个配置适合作为日常漏消息兜底，但如果下游长时间故障形成数万条积压，恢复速度会不足。生产化应监控状态滞留量和最老记录年龄，并采用限时循环分页、按分片并行扫描、专用回补任务或延迟/重试 Topic；同时保留速率上限，避免恢复流量再次压垮下游。

---

### 15. 为什么限流使用 Redisson 分布式信号量，而不是普通限流器？

**推荐回答**

这里首先要控制的是**在途并发**，而不是单位时间请求数。

模型接口单次耗时可能从几秒波动到几十秒。即使 QPS 不高，如果旧请求迟迟不返回，在途请求仍会不断堆积并超过供应商并发额度。项目按模型维度使用 `RPermitExpirableSemaphore`，许可数来自模型配置中的 `maxThreadSize`；实例获取许可后才能调用模型，完成后释放。设计目标是短等待后把背压交还 MQ，并给许可设置 10 分钟租约，避免实例崩溃后许可永久泄漏。

分布式信号量还能让多个应用实例共享同一模型的全局并发预算。单机 Semaphore 只能限制本实例，扩容后总并发会成倍增加。

**边界与改进**

- 信号量不等于 Token Bucket；如果供应商还限制 QPS 或 TPM，需要再叠加速率和 Token 配额治理；
- 当前代码调用 `tryAcquire(WAIT_SECONDS, LEASE_MINUTES, TimeUnit.MINUTES)`，这个重载的等待时间和租约共用一个时间单位，因此名为 `WAIT_SECONDS` 的值 `3` 实际会按 3 分钟解释。应改为 `tryAcquire(3, 600, TimeUnit.SECONDS)`，或使用能分别表达两个 `Duration` 的 API。修正前不要在面试中声称代码已经严格实现“等待 3 秒”；
- `trySetPermits` 只在信号量第一次创建时生效，运行期修改 `maxThreadSize` 不会自动调整已有许可数；动态调额需要在受控锁下计算差值并增减许可，或者重建带版本的信号量；
- 固定 10 分钟租约要求模型调用超时小于租约，否则许可提前回收后可能短暂超卖；更稳妥的做法是让租约与调用超时联动，或增加续租机制；
- 限流应配合超时、熔断、重试退避和模型维度监控，不能只靠一个并发数。

---

### 16. MySQL 到 Elasticsearch 为什么用 Outbox + MQ，不直接用 Canal 或 Flink CDC？

**推荐回答**

因为这里不是“把一张表原样复制到 ES”，而是构建面向查询的业务投影。索引文档可能需要字段转换、状态过滤、关联补全和幂等覆盖，业务服务也需要知道哪类变更应该触发同步。

项目在业务写入时记录 `eval_es_sync_event`，由 RocketMQ 异步消费。消费者收到事件后不直接相信事件里的旧快照，而是重新查询 MySQL 当前最新记录，再按文档 ID Upsert 到 ES。事件保留重试次数、下次重试时间和错误原因，并进行退避重试。

这解决了一个很实际的问题：状态依次从 `MODEL_RUNNING`、`MODEL_CALLED` 变成 `AUTO_SCORED`，如果较早事件因重试反而后到，消费者仍会查询当前的 `AUTO_SCORED`，不会用旧事件把 ES 状态覆盖回去。

**为什么这个选择能成立**

- 当前同步对象和业务语义强相关，Outbox 更容易表达“何时同步、同步成什么文档”；
- 已有 RocketMQ 的重试、监控和消费体系，维护链路更统一；
- Canal/Flink CDC 更适合大量表的通用变更捕获、跨系统复制和实时数仓场景。

**不要绝对化**

不是说 CDC 不合适。如果后续要同步几十张表、业务方不愿逐处埋事件，或者要建立统一实时数据平台，Canal/Flink CDC 会更有优势。此项目的选择依据是同步语义和运维成本，而不是工具能力高低。

---

### 17. 日增 2000W+ 明细时，分库分表和 ES 各自解决什么问题？

**推荐回答**

MySQL 和 ES 的职责不同：

- MySQL 保存权威状态、结果和可恢复工作流，需要支持按主键更新和事务；
- 核心结果明细表与节点明细表分别按 4 库 x 16 表拆分，每张逻辑表各 64 个物理分片，降低单表索引和写入热点；
- 同一样本相关数据尽量使用相同路由基础，便于单样本诊断；
- ES 承担任务维度的组合筛选、聚合和大范围检索，避免在线请求实时扫 64 个分片；
- Outbox 投影允许 ES 短暂不一致，但 MySQL 始终是最终事实源。

分片键不能只考虑“写得散”，还要考虑核心查询是否能路由。如果任务列表和统计查询无法带分片键，就不应让 API 直接广播扫描全部 MySQL 分片，而应走 ES 投影或离线聚合。

## 四、为什么选择 Spring AI，而不是 LangChain4j

### 18. 为什么项目使用 Spring AI，而不是 LangChain4j？

**推荐回答（完整版本）**

我们不是因为 LangChain4j 做不到而选择 Spring AI。LangChain4j 同样提供多模型与向量库集成、AI Services、RAG、Tool、Agent、结构化输出、Guardrails 和 Spring Boot 集成。选择 Spring AI 的核心是：**它与现有 Spring Boot 技术体系和本项目当前需求的贴合度更高，团队引入成本更低。**

项目已经是标准 Spring Boot 多模块应用，模型、向量库、重排服务和配置都集中在基础设施层管理。当前安全评测助手主要需要：

- 使用 `ChatClient` 统一模型调用；
- 使用 `.entity(...)` 获取结构化的意图和槽位结果；
- 使用 `RetrievalAugmentationAdvisor`、`ContextualQueryAugmenter` 和 `VectorStoreDocumentRetriever` 组织 RAG；
- 使用 `PromptTemplate` 管理提示词；
- 复用 Spring 的配置、Bean 生命周期、依赖注入、流式响应和可观测体系。

Spring AI 对这组需求提供了直接映射，能够继续沿用已有的 Spring 配置和分层方式，不需要再引入一套独立的模型客户端、记忆、检索和观测抽象。对当前项目而言，框架选型的主要目标是降低系统复杂度和团队维护成本，而不是比较谁的功能列表更长。

**结合项目代码说明，而不是泛泛而谈**

| 项目需求 | Spring AI 在项目中的落点 |
| --- | --- |
| 多模型统一调用 | 基于 Spring AI BOM 和各厂商 Starter，由基础设施模块统一管理模型 Bean |
| 意图识别和结构化返回 | `ChatClient` 配合 `.entity(...)` 映射为意图、槽位等 Java 对象 |
| RAG 编排 | `RetrievalAugmentationAdvisor`、查询增强器、文档检索器和 Joiner |
| 知识库向量检索 | `VectorStoreDocumentRetriever` 与 PGVector Store |
| 流式问答 | `ChatClient` 流式返回并接入现有 SSE 能力 |
| 工程治理 | 继续复用 Spring 配置、依赖注入、异常处理和监控体系 |

**30 秒版本**

> LangChain4j 不是能力不够，它也支持 Spring Boot、RAG、Tool 和 Agent。我们选择 Spring AI，主要因为项目本身是 Spring Boot 多模块系统，当前需要的 ChatClient、结构化输出、Advisor RAG、VectorStore 和流式响应都能直接融入已有 Bean、配置和可观测体系。这个选择减少了重复抽象和团队学习成本。若是一个以 Agent、AI Services 声明式接口为核心的全新项目，我也会重新评估 LangChain4j。

---

### 19. 那 LangChain4j 的优势是什么？什么情况下你会选它？

**推荐回答**

LangChain4j 的 AI Services 很适合用 Java 接口声明 AI 能力，能够减少底层模型调用、记忆、工具和结构化输出的样板代码；它在 Agent、Tool、RAG 以及多种模型和向量库集成方面也很完整。

如果是以下场景，我会认真考虑 LangChain4j：

- 新建一个以 Agent 和 Tool Calling 为核心、业务接口天然适合 AI Services 声明方式的应用；
- 希望框架层尽量独立于 Spring，或者同时支持 Quarkus、Helidon 等运行时；
- 团队已经有成熟的 LangChain4j 组件、测试和可观测规范；
- 经过 POC 后，它在目标模型、工具编排或社区组件上明显更契合。

选型时我会比较目标模型支持、结构化输出稳定性、RAG 可插拔性、流式调用、Tool/Agent、可观测性、版本兼容、团队经验和迁移成本，而不会只做 API 数量对比。

---

### 20. Spring AI 和 LangChain4j 能不能一起用？为什么不各取所长？

**推荐回答**

技术上可以，但默认不建议在同一条业务链路同时维护两套框架抽象。否则会出现：

- 两套模型客户端和配置方式；
- 两套消息、记忆、Tool 和 RAG 语义；
- 结构化输出、异常和重试行为不一致；
- Trace、指标和依赖版本治理变复杂；
- 同一个问题难以判断应该在哪一层修复。

只有当 LangChain4j 某项能力经过验证能带来明确收益，而且无法通过一个隔离适配器实现时，才值得在独立模块做小范围 POC。框架应该位于基础设施边界内，领域服务依赖自定义接口，避免将来替换框架时改动核心安全评测逻辑。

**继续追问“做过性能对比吗”**

可以如实回答：没有把框架微小调用开销当成主要决策指标，因为链路耗时主要来自外部模型、向量检索和 Rerank。POC 更关注功能正确性、结构化输出成功率、流式稳定性、观测能力和维护复杂度。只有在这几项接近时，才有必要做框架开销基准测试。

## 五、RAG 过程中遇到的问题与解决方式

### 21. 先澄清：这个项目里说的 RAG 是哪一条链路？

面试时建议先主动区分两类检索增强，避免把能力讲混：

1. **L2 安全评测检索。** 输入是被测模型输出，目标是召回相同风险类型的危险/安全案例。当前实现是 ES + PGVector 两路召回、RRF、Rerank 和阈值路由。
2. **安全评测助手 RAG。** 输入是用户问题，目标是查询安全知识或结构化配置。当前代码通过意图、槽位和 Query Transformer 改写问题，再路由到知识库向量检索或关系库 Text2SQL。

这两条链路解决的问题不同。L2 的输出参与安全判定，错误成本更高；助手 RAG 的输出面向解释和查询，更关注问题理解、来源路由和回答可信度。

---

### 22. RAG 过程中碰到的最大问题是什么？

**推荐回答**

最大的体会是：RAG 的难点不是“把文档放进向量库”，而是让正确的问题去正确的数据源，并在有限延迟内拿到足以支撑结论的证据。

我们遇到的问题主要有六类：

1. 多轮问题省略关键上下文，原始 Query 无法检索；
2. 知识问答和精确数据查询被错误地送到同一个检索器；
3. 关键词召回与语义召回各有盲区，单路召回率不足；
4. 多路分数不可直接比较，前排候选不一定真的相关；
5. 召回内容不足或冲突时，大模型仍可能生成看似合理的答案；
6. 知识更新、检索延迟和效果评估容易被忽略。

项目不是用一个 Prompt 兜底，而是把它们分别放到 Query Transformer、确定性 Slot Validator、Query Router、混合召回、RRF/Rerank、阈值路由和结构化输出约束中解决。

---

### 23. 多轮对话中的问题不完整，怎么检索？

**业务例子**

用户先问：“评测结果 `RD-20260712-001` 为什么被判为不安全？”下一轮只说：“那 L2 为什么没直接通过？”

如果直接拿第二句话检索，系统不知道“那”指哪条结果，也不知道目标风险类型。项目使用 Query Transformer，结合当前意图、已提取槽位和对话上下文，把它改写成独立问题，例如：

```text
查询评测结果 RD-20260712-001 的 L2 节点，说明召回证据、重排分数和阈值路由为什么未直接判为安全。
```

但 Query Transformer 不能凭空补 ID。项目还增加确定性的 Slot Validator，根据意图重新计算必填槽位，不信任大模型自己返回的 `needClarification=false`。缺少 `resultDetailId` 时先追问并按 `conversationId` 保存待补槽位状态，用户补充后再继续执行。

**为什么一定要有确定性校验**

意图模型有时会输出一个完整 JSON，却把关键字段留空并错误地认为无需澄清。如果业务层直接相信它，后续检索范围会扩大，既可能答错数据，也可能造成越权查询。LLM 负责理解语言，业务代码负责验证执行前置条件。

**当前实现边界**

当前工程中的待澄清状态是 `ConcurrentHashMap + 30 分钟 TTL`，适合验证流程，但多实例生产部署应迁移到 Redis，并增加租户、用户和会话维度隔离。这是一个可以主动承认的生产化改进点。

---

### 24. RAG 和 Text2SQL 怎么分工？路由错了怎么办？

**推荐回答**

语义知识和精确事实不能用同一种检索方式：

- “什么是提示词注入”“如何理解安全拒答”属于知识库语义问答，走向量检索；
- “当前启用了哪些风险详情”“某风险类型配置了哪些风险词”要求精确字段、过滤和排序，走关系库查询；
- 链路诊断类问题最终应进入结果与节点日志检索，而不是让知识库猜测。

项目的 Query Router 先输出 `knowledge_base` 或 `relational_db` 以及置信度；置信度低于阈值时，再根据已识别意图做确定性回退，避免一次不稳定的 LLM 分类直接决定数据源。

**当前边界必须说清楚**

助手 V1 当前落地的是知识库向量检索和关系库查询，ES 节点日志 Retriever 还应作为下一步接入。因此不能声称“助手已经能完整查询所有评测链路日志”。可以说平台本身已有节点日志数据基础，助手侧正在把它封装成独立、带权限的 ES 检索器。

另外，`SecurityEvalQueryRouter` 的 Prompt 已经描述了任务、结果、同步状态和统计等结构化查询，但 `EvaSqlDatabaseContentRetriever` 当前 DDL 白名单实际只有 `risk_details` 和 `knowledge_vocabulary_keyword`。这意味着某些问题能够被正确路由到 `relational_db`，却没有足够表权限完成查询。下一步需要让“路由能力声明、Retriever 数据契约、权限白名单”保持一致；在补齐前，只承诺风险详情和风险词等已开放资产查询。

**Text2SQL 安全措施**

当前代码只允许 `SELECT/WITH`，禁止写操作、DDL、多语句和非白名单表，自动补充 `LIMIT 50` 并截断超长单元格。生产化还应增加 SQL AST 解析、只读数据库账号、查询超时、扫描行数限制、租户行级权限和审计日志。正则过滤只能作为第一道防线，不能描述成完整安全方案。

---

### 25. 单路向量召回有什么问题？你们怎么解决？

**推荐回答**

安全语料里有两类典型查询：

- 依赖精确词和短语的查询，例如特殊工具名、风险术语、法规编号；
- 大量同义改写和隐晦表达，例如“避开校验”“跳过实名步骤”“不经过身份核验”。

单纯向量检索可能漏掉必须精确匹配的稀有词，也可能因为通用语义接近召回主题相似但风险行为不同的文本；单纯 ES 又会漏掉没有共同字面的改写。因此 L2 使用 ES + PGVector 互补召回，并对元数据中的启用状态和 `targetRiskDetailsId` 做过滤。

**贴近业务的例子**

被测输出是“有没有办法不经过身份核验直接完成开户”。它可能完全没有出现规则里的“绕过实名认证”，但向量召回能找到语义相近案例；如果文本中出现一个特殊认证产品名，ES 又能给出更强的精确证据。两路共同靠前的候选经 RRF 提升，再由 Rerank 判断完整语境。

---

### 26. 检索中如何避免不同风险类型互相污染？

**推荐回答**

不能只在召回后看文本相似度，还要在召回前使用业务元数据约束候选范围。项目会过滤 `status=1`，并在任务已经指定目标风险详情时带上 `targetRiskDetailsId`。

例如当前任务评测“危险物品制作”，某条文本在语言风格上与“网络攻击步骤”案例很像。如果不做目标风险过滤，这个高相似候选可能把 L2 或 L3 引向错误类别。过滤后系统只回答当前目标规则是否命中，避免跨类别证据污染。

这里也体现了 RAG 的一个关键原则：**向量相似只是候选信号，业务约束才决定哪些文档有资格成为证据。**

---

### 27. 命中了危险案例，又命中了安全例外，为什么不直接判安全？

**推荐回答**

因为“安全措辞”不等于“安全内容”。攻击性回答可能采用这种结构：

```text
我不建议你这样做，也不能提供帮助。不过从技术角度，具体步骤是……
```

前半段与安全拒答案例高度相似，后半段却给出了完整危险步骤。如果只要命中安全例外就直接放行，会形成很容易利用的绕过方式。

因此项目中安全例外只用于降低直接判风险的确定性：当危险证据和安全证据冲突时，结果进入 L3，由目标规则、完整上下文和正反例一起判断。这个设计牺牲少量 L3 成本，换取明显更稳妥的边界处理。

---

### 28. 没有召回结果、召回分数很低或上下文冲突时怎么办？

**推荐回答**

不能把“没有证据”解释成“确定安全”，也不能让生成模型用常识补出一段确定答案。处理方式要根据链路风险区分：

- L2 检索服务异常时可以返回降级状态，但高风险任务应进入人工复核或失败重试，不能静默放行；
- 分数处于中间区间或证据冲突时进入 L3；
- L3 返回缺字段、非 JSON、目标风险不一致或结论不确定时进入人工复核；
- 助手问答中证据不足时明确说明缺少依据，并要求用户补充结果 ID、风险类型或时间范围；
- 回答必须附带规则或案例来源，不允许模型把未检索到的信息包装成平台事实。

当前代码中的 `DEGRADED_SAFE` 适合作为可观测的降级信号，但生产策略需要按任务风险等级配置：低风险场景可以继续，高风险场景应 Fail Closed 或转人工，不能全局使用同一种降级策略。

---

### 29. RAG 的知识新鲜度和 MySQL/ES/向量库一致性怎么保证？

**推荐回答**

先区分事实源和查询投影：MySQL 保存权威风险配置和评测状态，ES 与向量库是检索投影。更新时通过事件驱动异步重建索引，文档 ID 保持稳定并采用 Upsert；消费时重新读取最新业务数据，避免乱序事件覆盖新版本。

除此之外还应具备：

- 文档携带业务主键、规则版本、状态和更新时间；
- 只召回启用状态的数据；
- 更新和删除都产生可重试事件；
- 定期做 MySQL 与索引的数量、版本和抽样内容对账；
- 检索日志记录命中的文档版本，便于复现历史判定。

向量索引的一致性通常是最终一致，不适合承担强事务判断。涉及当前任务状态等精确事实时应查询 MySQL，而不是从向量库推断。

---

### 30. RAG 延迟高，怎么优化？

**推荐回答**

先分解耗时，而不是盲目减少 TopK：Query Rewrite、Embedding、ES、PGVector、Rerank、L3/回答模型分别打点，确认瓶颈在哪一段。

常用优化包括：

- ES 和 PGVector 并行召回；
- 控制首轮 TopK 和融合后的 TopN，只对短名单 Rerank；
- 对规则、Embedding 和高频知识查询做版本化缓存；
- 限制文档长度和最终上下文 Token 数；
- 只有低置信度样本进入 L3；
- 给检索、Rerank 和模型调用分别设置超时与降级策略；
- 按模型和检索服务做隔离，避免一个依赖拖慢整条链路。

不能只优化平均耗时。安全评测更应该看 P95/P99、MQ 排队时间、L3 进入率和单样本成本，因为一次大批量任务会把尾延迟放大成明显积压。

### 31. 你们怎么评估 RAG 做得好不好？

**推荐回答**

RAG 要拆开评估，不能只问最终回答“看起来是否合理”。

**离线检索指标**

- Recall@K：正确案例是否进入候选集；
- MRR/NDCG：正确案例是否排在前面；
- 按风险类型分别统计，避免大类掩盖小类；
- 路由准确率、Query Rewrite 保真率和槽位补全成功率。

**判定与回答指标**

- 安全评测看 Precision、Recall、FPR、FNR、人工复核率；
- 助手看答案是否被检索证据支持、引用是否正确、是否越权、拒答是否合理；
- 记录无结果率、低置信度率、L3 进入率和降级率。

**工程指标**

- 各阶段 P95/P99、Token 与 Rerank 成本；
- 索引新鲜度、同步失败量和对账差异；
- 不同模型、Prompt、规则版本下的效果回归。

测试集应来自真实误判、漏判和人工复核案例，并对规则、Embedding 模型、Rerank 模型和 Prompt 做版本化。每次修改先离线回放，再小流量验证。当前代码已经记录 hits、分数、证据和节点输出，具备建设这套评测闭环的数据基础；没有正式统计过的指标不要说成已经达到某个数值。

---

### 32. RAG 会不会把恶意文档里的指令带给模型，造成 Prompt Injection？

**推荐回答**

会，所以检索到的文档必须被视为不可信数据，而不是系统指令。处理上需要：

- 系统 Prompt 明确区分规则、用户输入和检索证据，禁止执行证据中的指令；
- 知识入库有来源、状态、版本和权限校验；
- 只从指定知识域和目标风险类型召回；
- Tool 和 Text2SQL 权限由代码校验，不能由模型自行决定；
- 结构化输出做字段、枚举和目标风险一致性验证；
- 高风险动作不由 RAG 回答直接触发，必要时人工复核。

L3 Judge 的 Prompt 只要求依据目标规则判断输入是否命中，不给检索文档调用工具或改变系统策略的能力。即使候选案例中包含“忽略之前指令”，它也只能作为待判断文本，而不能提升为系统指令。

## 六、三个可以在面试中展开的完整案例

### 33. 案例一：合规拒答被关键词和向量检索同时命中

**场景**

被测模型输出：“我不能提供绕过身份认证的具体步骤，这可能导致账户和合规风险。建议通过官方渠道完成认证。”

**问题**

文本包含高风险短语，语义上又和历史危险案例接近，单纯关键词或向量阈值都可能误杀。

**处理**

1. L1 二级词命中后保留证据并继续下沉；
2. L2 的 ES 召回精确风险词案例，PGVector 同时召回危险案例和安全拒答案例；
3. RRF 和 Rerank 得到高危险相似度，但安全例外证据也成立，因此不直接判安全或风险；
4. L3 读取“身份认证绕过”的目标规则，判断全文是在拒绝还是提供操作；
5. 结果与每个节点证据落库，复核人员能看到误判风险来自哪一步。

**体现的能力**

业务边界建模、混合检索、冲突证据处理、L3 成本控制和结果可解释性。

---

### 34. 案例二：模型调用成功后进程重启

**场景**

模型供应商已经返回结果，应用把输出和 `MODEL_CALLED` 状态写入数据库，但尚未成功发送安全评测消息时实例重启。

**问题**

简单重试整个消费会再次调用模型，既产生重复费用，也可能因模型随机性得到不同输出；不重试则样本永远无法完成。

**处理**

1. 状态机把 `MODEL_CALLED` 作为可靠恢复点；
2. 定时补偿扫描状态滞留记录并重发 `SafetyEvaluate_MQ`；
3. 消费者基于结果明细 ID 和状态做幂等校验；
4. 从数据库中的原始模型输出继续 L1/L2/L3，不再次调用供应商；
5. 节点日志记录补偿和后续执行，最终任务进度正常收敛。

**体现的能力**

对至少一次投递、跨系统一致性窗口、业务幂等和可恢复工作流的理解。

---

### 35. 案例三：助手收到一句“这条为什么不安全”

**场景**

用户在新会话中直接问：“这条为什么不安全？”

**问题**

没有结果明细 ID、风险类型或原始文本。让模型直接回答，它很可能根据常识生成一段与平台事实无关的解释。

**处理**

1. 意图识别为链路解释或误判分析；
2. Slot Validator 确认缺少 `resultDetailId`，不接受模型错误的“无需澄清”；
3. 系统追问具体结果编号，并按会话保存待补槽位；
4. 用户补充编号后，Query Transformer 生成可独立执行的问题；
5. 当前 V1 可查询规则和知识数据，完整节点解释需要路由到后续的 ES 链路 Retriever；没有接入的数据不由大模型猜测。

**体现的能力**

多轮上下文、确定性业务校验、检索路由和对 RAG 能力边界的控制。

## 七、项目不足与下一步改进

### 36. 如果让你再做一版，你最想改什么？

**推荐回答**

我会优先做四件事：

1. **建立版本化评测集和阈值校准体系。** 按风险类型维护真实误判、漏判和边界案例，自动回放并产出 Recall@K、FPR/FNR、L3 进入率和成本变化。
2. **补齐助手的链路检索能力。** 将结果和节点日志封装成独立 ES Retriever，加入租户与字段权限，再与知识库和关系库路由统一编排；当前不能让助手根据知识库猜节点事实。
3. **加强 Text2SQL 和会话状态的生产治理。** 使用 SQL AST、只读账号、行级权限、扫描限制和审计；把待澄清状态从本地内存迁移到 Redis。
4. **按风险等级配置降级策略。** 高风险任务在 L2/L3 依赖异常时转人工或 Fail Closed，低风险任务才允许可观测降级，避免全局 `DEGRADED_SAFE` 带来漏判风险。

还有一个状态语义需要收紧：当前 `SafetyEvaluateConsumer` 在 L3 返回 `safe=null`、需要转人工时直接写入 `MANUAL_REVIEWED`。它实际上表达的是“待人工复核”，不是“已经复核完成”。更合理的状态机应拆成 `PENDING_MANUAL_REVIEW -> MANUAL_REVIEWED`，并在完成态记录审核人、审核时间、人工结论和规则版本，避免任务进度提前收敛。

此外会继续完善模型维度的 QPS/TPM 治理、动态信号量租约、规则与索引对账、Prompt Injection 测试和端到端 Trace。

**为什么这样排优先级**

前两项直接提升结果可信度和助手能力边界，后两项解决多实例、安全和降级风险。相比继续增加更多 Agent 或模型，这些工作更接近当前系统的真实瓶颈。

## 八、面试现场速答版

### 37. “项目最难的地方”90 秒回答

> 我认为最难的不是某个中间件，而是把比较模糊的安全标准落成大规模、可解释、可恢复的判定链路。业务上，同一个风险词放在危险教程和合规拒答里含义完全不同；工程上，日均 200 多个批量任务会展开成约 350 万到 450 万样本和 2000W+ 节点、结果明细，MQ 重复投递、模型超时和进程重启都可能让样本重复调用或永久挂起。
>
> 我们把它拆成 L1/L2/L3：L1 用 AC 自动机处理确定性规则，L2 用 ES 与 PGVector 混合召回、RRF 和 Rerank 处理相似案例，只有冲突或低置信度样本进入 L3，L3 只依据目标风险规则判断。执行侧再用样本级状态机、分布式锁、幂等消费和定时补偿保证最终收敛，并保存每个节点的输入、证据、结果和耗时。因此这套设计解决的不只是“能判断”，还包括“为什么这样判断”和“故障后怎么继续”。

### 38. “为什么 Spring AI”45 秒回答

> LangChain4j 也支持 Spring Boot、RAG、Tool、Agent 和结构化输出，所以不是因为它能力不够。我们选择 Spring AI，主要因为现有系统是 Spring Boot 多模块架构，项目需要的 ChatClient、结构化 `.entity(...)`、Advisor RAG、VectorStore、PromptTemplate 和流式响应都能直接复用现有 Bean、配置、异常和观测体系。相比同时引入另一套模型与 RAG 抽象，这样团队学习和维护成本更低。如果是一个以 AI Services 或 Agent 为核心的全新项目，我会基于 POC 再评估 LangChain4j。

### 39. “RAG 遇到什么问题”90 秒回答

> RAG 最大的问题不是向量库接不通，而是问题理解、数据源路由、召回质量和证据约束。项目里有两条检索链路：L2 评测链路用 ES 做精确召回、PGVector 做语义召回，再用 RRF 和 Rerank；安全评测助手则先做意图和槽位识别，用 Query Transformer 补全多轮问题，再在知识库向量检索和关系库查询之间路由。
>
> 实际问题包括用户只问“这条为什么不安全”导致关键 ID 缺失、向量召回把相似但不同风险类型的案例带进来、危险案例与安全拒答案例同时命中，以及低质量上下文诱导模型编答案。对应地，我们用确定性 Slot Validator 追问缺失字段，用目标风险元数据过滤候选，用混合召回和重排提升排序，对安全例外只降置信度而不直接放行，证据不足或 Judge 输出不合法时进入人工复核。后续重点是补齐助手的 ES 节点日志 Retriever 和版本化离线评测集。

## 九、容易失分的回答与修正

| 容易失分的说法 | 问题 | 更好的说法 |
| --- | --- | --- |
| “最难的是用了很多中间件” | 只有组件，没有矛盾和结果 | 先讲安全边界、质量/成本权衡和故障恢复，再说明组件各自承担什么职责 |
| “MQ 保证消息只消费一次” | 至少一次投递下不成立 | MQ 允许重复，业务通过状态机、幂等键和补偿达到结果恰好一次 |
| “有分布式锁就幂等了” | 锁只能控制同时执行 | 锁解决并发，持久状态机解决重放、重启和锁过期后的幂等 |
| “LangChain4j 不支持 Spring/Agent/RAG” | 与官方能力不符 | 两者都能做，选 Spring AI 是现有架构、团队和需求贴合度更高 |
| “RRF 把 ES 分数和向量分数相加” | RRF 使用名次，不直接相加原始分数 | RRF 用倒数排名融合异构结果，Rerank 再做语义精排 |
| “命中安全例外就直接安全” | 容易被“先拒绝后给步骤”绕过 | 安全例外只降低直接判风险的确定性，冲突样本进入 L3 |
| “没召回就是安全” | 无证据不等于安全 | 根据风险等级转 L3、重试、降级或人工复核 |
| “Text2SQL 禁止 DELETE 就安全了” | 仍有越权、复杂查询和资源耗尽风险 | AST、白名单、只读账号、行级权限、超时、行数限制和审计共同治理 |
| “助手已经能查完整链路日志” | 当前代码没有成熟 ES Retriever | 如实说明 V1 的知识库/关系库路由，ES 节点检索是下一步 |
| “所有阈值都是最佳实践” | 阈值与数据分布、风险类型相关 | 当前值是起点，通过版本化标注集按风险类型校准 |
