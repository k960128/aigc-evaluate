## 二、Java 基础与集合

### 1. `==`、`equals()` 和 `hashCode()` 有什么区别？

**答：**基本类型的 `==` 比较值，引用类型的 `==` 比较是否为同一对象。`equals()` 表达业务相等语义，默认实现仍是引用相等。对象如果重写 `equals()`，必须同步重写 `hashCode()`，保证相等对象哈希值相等，否则放入 HashMap、HashSet 后可能无法正确查找或去重。

**追问：**哈希值相等不代表对象相等；可变字段不适合参与哈希计算，否则对象放入集合后修改字段会破坏桶位置。

### 2. 为什么 String 不可变？有什么好处？

**答：**String 内部值创建后不可修改，拼接、替换都会产生新对象。不可变带来线程安全、可缓存 hash、适合作为 HashMap Key、字符串常量池可复用，也能避免类名、文件路径、URL 等安全敏感值被引用方修改。

**追问：**循环拼接使用 StringBuilder；多线程共享拼接才考虑 StringBuffer。`String.intern()` 返回常量池中的规范引用，大量动态字符串滥用 intern 会增加常量池和哈希表压力。

### 3. Java 泛型为什么是类型擦除？有什么限制？

**答：**Java 泛型主要在编译期检查，编译后大部分类型参数会擦除为上界或 Object，以兼容旧字节码。限制包括不能直接 `new T()`、不能创建泛型数组、不能用基础类型作为类型参数、运行时通常无法判断 `List<String>` 与 `List<Integer>`。

**追问：**反射可从字段、方法签名的 Signature 元数据读取声明泛型，但对象实例本身通常不保留实参类型。PECS 原则是 Producer Extends、Consumer Super。

### 4. checked exception 和 unchecked exception 如何选择？

**答：**checked exception 强制调用方处理，适合调用方确实能够恢复的外部条件；RuntimeException 适合参数错误、状态错误、编程缺陷和无法合理恢复的问题。业务系统通常定义统一业务异常，由全局异常处理器转换为稳定错误码。

**追问：**不要捕获 Exception 后吞掉；保留 cause、业务标识和上下文。finally 中 return 会覆盖原返回值和异常，应避免。

### 5. 反射的原理、成本和使用场景是什么？

**答：**反射通过 Class 元数据动态发现并调用构造器、字段和方法，框架的依赖注入、ORM、序列化和测试工具都会使用。主要成本是访问检查、动态分派、装箱以及 JIT 优化难度，但现代 JDK 对热点反射已有优化，不能简单说“反射一定慢很多”。

**追问：**高频路径可缓存 Method、Constructor 或使用 MethodHandle；模块系统下还要考虑可访问性。反射绕过封装能力强，因此要限制输入和权限。

### 6. JDK 动态代理和 CGLIB 有什么区别？

**答：**JDK 动态代理基于接口生成代理类，调用进入 InvocationHandler；CGLIB 通过生成目标类子类覆盖方法，因此不能代理 final 类和 final 方法。Spring 有接口时通常可使用 JDK 代理，没有接口时使用 CGLIB。

**追问：**无论哪种代理，自调用都可能绕过代理对象，导致事务或切面失效。代理解决横切逻辑，不应把核心业务全部堆进切面。

### 7. ArrayList 和 LinkedList 如何选择？

**答：**ArrayList 基于连续数组，随机访问 O(1)，缓存局部性好，尾部追加均摊 O(1)；中间插入需要移动元素。LinkedList 节点分散，定位 O(n)，每个节点还有前后指针内存开销。实际业务绝大多数场景优先 ArrayList，不能只因“中间插入 O(1)”就选择 LinkedList，因为找到插入位置仍需 O(n)。

### 8. HashMap 的底层结构和 put 流程是什么？

**答：**JDK 8 以后由数组、链表和红黑树组成。put 时对 hash 做扰动，定位桶；空桶直接插入，冲突时比较 hash 和 equals，存在则覆盖，否则追加。链表长度达到 8 且数组容量至少 64 时树化；元素数量超过 `capacity * loadFactor` 时扩容，默认负载因子 0.75。

**追问：**树节点减少极端冲突下的查询退化，但内存更高；容量较小时优先扩容而非树化。HashMap 不是线程安全的。

### 9. HashMap 为什么容量通常是 2 的幂？如何扩容？

**答：**桶下标通过 `(n - 1) & hash` 计算，容量为 2 的幂时可以用位运算代替取模，并让低位分布充分参与。扩容通常翻倍，旧桶中的节点根据新增高位是 0 还是 1，留在原索引或移动到 `oldIndex + oldCapacity`，不需要重新完整取模。

**追问：**已知数据规模时可预估初始容量，减少扩容和对象搬迁；但过度预分配会浪费内存。

### 10. ConcurrentHashMap 如何保证线程安全？

**答：**JDK 8 使用 Node 数组、链表/红黑树、CAS 和桶级 synchronized。初始化和部分状态更新依赖 CAS；桶冲突时锁住首节点，而不是锁整张表；读操作大多依赖 volatile 可见性，无需加全局锁。扩容时多个线程可以协助迁移。

**追问：**它不允许 null Key/Value，避免并发读取时无法区分“没有映射”和“值为 null”。复合操作应使用 `computeIfAbsent`、`merge` 等原子 API，不能先 get 再 put。

### 11. fail-fast 和 fail-safe 是什么？

**答：**ArrayList、HashMap 迭代器通常通过 modCount 检测结构修改并抛出 ConcurrentModificationException，它是尽力而为的错误检测，不是线程安全机制。CopyOnWriteArrayList 迭代的是旧数组快照，遍历不受并发写影响，通常称弱一致或快照迭代。

### 12. CopyOnWriteArrayList 适合什么场景？

**答：**适合读多写少、集合规模不大、允许读取短暂旧数据的场景，例如监听器列表。写操作复制整份数组并加锁，内存和复制成本高，因此不适合高频写、大集合或强实时一致性。

### 13. TreeMap、PriorityQueue 和 HashMap 的使用边界是什么？

**答：**HashMap 适合按 Key O(1) 期望复杂度访问；TreeMap 基于红黑树，提供 O(log n) 有序查找、范围查询；PriorityQueue 基于堆，只保证堆顶最小或最大，不保证全局遍历有序。TopK 用 PriorityQueue 往往比全量排序更节省空间。

### 14. 如何设计一个不可变对象？

**答：**类尽量 final，字段 private final，构造时完成校验，不提供修改方法；对 List、Map、数组、Date 等可变对象做防御性拷贝，getter 返回不可变视图或副本。不可变对象天然便于并发共享，但每次变更创建新对象可能增加分配成本。

## 三、Java 并发与 JUC

### 15. 什么是 Java 内存模型？

**答：**JMM 定义线程如何通过主内存交互，以及可见性、有序性和原子性规则。每个线程可能使用寄存器、CPU 缓存或编译器优化后的工作副本；没有同步关系时，一个线程的写不保证立即被另一个线程观察到。

**追问：**JMM 不是 JVM 运行时内存区域。解决并发正确性要建立 happens-before，而不是依赖“通常能看到”。

### 16. happens-before 有哪些常见规则？

**答：**程序次序规则、监视器解锁先于后续加锁、volatile 写先于后续读、线程 start 前操作先于子线程动作、子线程动作先于 join 返回、传递性。happens-before 同时约束可见性和必要的排序关系。

### 17. volatile 能保证什么？不能保证什么？

**答：**volatile 保证写对后续读可见，并禁止相关指令重排，适合状态标志、一次写多次读和单变量发布。它不能保证复合操作原子性，`count++` 仍包含读、加、写三个步骤。

**追问：**DCL 单例中的实例字段必须 volatile，防止引用赋值与对象初始化重排，使其他线程看到半初始化对象。

### 18. synchronized 的底层原理是什么？

**答：**同步代码块通过 monitorenter/monitorexit，方法通过 ACC_SYNCHRONIZED 标志。锁对象关联监视器，进入和退出锁同时建立内存屏障。JVM 会做锁消除、锁粗化、自适应自旋等优化；现代 JDK 已移除或关闭偏向锁，不要机械背诵固定的“偏向锁升级链”。

**追问：**synchronized 可重入，异常退出也会释放锁；锁粒度过大影响并发，锁粒度过细增加复杂性和死锁风险。

### 19. synchronized 和 ReentrantLock 如何选择？

**答：**简单互斥优先 synchronized，语法安全且 JVM 优化充分。需要可中断获取、超时、尝试锁、公平锁或多个 Condition 时使用 ReentrantLock。ReentrantLock 必须在 finally 中 unlock。

**追问：**公平锁降低饥饿但吞吐通常更低；不能仅因“性能更高”选择 ReentrantLock，现代 synchronized 在多数场景性能很好。

### 20. AQS 的核心设计是什么？

**答：**AQS 用一个 volatile state 表示同步状态，使用 CAS 修改；获取失败的线程进入 CLH 变体的 FIFO 等待队列并 park，释放资源后唤醒后继。子类实现 tryAcquire/tryRelease 或共享模式方法。ReentrantLock、Semaphore、CountDownLatch 都基于 AQS。

**追问：**独占模式同一时刻一个线程持有；共享模式允许多个线程共同获取。Condition 有独立条件队列，signal 后节点还要转移到同步队列竞争锁。

### 21. CAS 有什么问题？ABA 如何解决？

**答：**CAS 是比较期望值并原子更新，避免阻塞，但高竞争会自旋消耗 CPU，只适合短小状态更新。ABA 指值从 A 变 B 又变 A，CAS 无法发现中间变化。可使用 AtomicStampedReference 增加版本号，或通过业务唯一版本解决。

### 22. AtomicLong 和 LongAdder 有什么区别？

**答：**AtomicLong 在单个变量上 CAS，高竞争时大量线程争用同一缓存行；LongAdder 将更新分散到 base 和多个 Cell，读取时求和，吞吐更高但 sum 不是严格瞬时原子快照。计数指标适合 LongAdder，账户余额等强一致值使用 AtomicLong 或锁。

### 23. Java 线程有哪些状态？如何正确中断线程？

**答：**NEW、RUNNABLE、BLOCKED、WAITING、TIMED_WAITING、TERMINATED。interrupt 只是设置中断标志或让 sleep/wait/join 抛 InterruptedException，不会强制杀死线程。捕获 InterruptedException 后如果不能结束，应调用 `Thread.currentThread().interrupt()` 恢复标志。

### 24. ThreadPoolExecutor 的核心参数是什么？

**答：**corePoolSize、maximumPoolSize、keepAliveTime、TimeUnit、workQueue、threadFactory、rejectedExecutionHandler。提交顺序是先创建核心线程，再入队，队列满后扩到最大线程，仍无法接收才触发拒绝策略。

**追问：**无界队列会让 maximumPoolSize 失效并可能 OOM；线程数不能只套公式，要根据 CPU、I/O 等待、下游容量和压测结果决定。

### 25. 线程池队列和拒绝策略如何选择？

**答：**ArrayBlockingQueue 有界且内存可控；LinkedBlockingQueue 默认近似无界，必须显式容量；SynchronousQueue 不存任务，直接交接。AbortPolicy 快速失败，CallerRunsPolicy 让提交线程执行形成背压，Discard/DiscardOldest 只能用于允许丢弃且有监控的业务。

**追问：**在线业务通常使用有界队列、命名线程工厂、明确拒绝策略和指标监控，不能直接使用 Executors 默认工厂隐藏队列风险。

### 26. 如何动态调整线程池？

**答：**ThreadPoolExecutor 支持运行时调整 core/max、keepAlive 等参数，但调整依据应是队列长度、任务等待时间、执行耗时、拒绝数、CPU 和下游负载。核心线程数不能大于最大线程数，缩容还要考虑正在执行任务。

**追问：**动态调参不是自动解决容量问题。下游数据库或模型接口已到上限时，扩大线程池只会增加排队和超时。

### 27. ThreadLocal 为什么会内存泄漏？

**答：**ThreadLocalMap 的 Key 是弱引用，ThreadLocal 无外部引用后 Key 可被回收，但 Value 仍由长生命周期线程强引用，直到访问时清理或线程结束。线程池线程长期存在，因此必须在 finally 中 remove。

**追问：**ThreadLocal 适合请求上下文、TraceId 等线程绑定数据；异步切线程时不会自动传播，需要显式传递或使用上下文传播组件。

### 28. CompletableFuture 常见问题有哪些？

**答：**`thenApply` 做同步转换，`thenCompose` 展平异步任务，`thenCombine` 合并独立结果，`allOf` 等待多任务。常见问题是默认使用公共 ForkJoinPool、调用 join 阻塞、异常未处理、任务无超时、线程池与业务隔离不足。

**追问：**生产中应传入专用有界线程池，使用 orTimeout/completeOnTimeout，统一 exception/handle，并避免在同一小线程池内等待彼此。

### 29. 如何排查死锁？如何避免？

**答：**使用 `jstack`、`jcmd Thread.print` 或监控平台查看线程等待关系，JVM 通常能标出 Java 层死锁。避免方式包括固定锁顺序、减少嵌套锁、使用 tryLock 超时、缩小临界区、避免持锁调用远程服务。

### 30. CountDownLatch、CyclicBarrier、Semaphore 有什么区别？

**答：**CountDownLatch 等待一组事件完成，计数归零后不能重置；CyclicBarrier 让一组线程互相等待到达屏障，可重复使用；Semaphore 控制同时访问资源的许可数量。分布式模型并发控制需要跨进程信号量，本地 Semaphore 不够。

### 31. 什么是伪共享？如何处理？

**答：**不同线程频繁写同一缓存行中的不同变量，会造成缓存行反复失效。可通过字段填充、`@Contended`、减少共享写、分片计数等方式缓解。LongAdder 的 Cell 分散就是典型思路。

### 32. 乐观锁和悲观锁如何选择？

**答：**悲观锁假设冲突多，先加锁再操作，适合高冲突和短事务；乐观锁通过版本号或 CAS 检测冲突，适合读多写少，但失败后需要重试。重试必须有次数上限和退避，否则高冲突下可能形成活锁。

### 33. Java 21 虚拟线程适合什么场景？

**答：**虚拟线程适合大量阻塞 I/O 任务，让代码保持同步写法而不需要为每个请求占用平台线程。它不能让 CPU 密集计算更快，也不能突破数据库连接池、远程模型并发等下游容量。

**追问：**避免在虚拟线程中长时间持有 synchronized 监视器或执行无法卸载的本地调用导致 pinning。ThreadLocal 大量数据也会因虚拟线程数量巨大增加内存成本。

### 34. 如何保证多个异步任务中只要一个失败就快速结束？

**答：**为每个任务设置超时和取消策略，使用 CompletableFuture 的异常回调或结构化并发思想统一管理生命周期。`allOf` 默认只表示全部完成，不会自动取消其他任务；需要在任一失败时主动 cancel，并确保底层客户端支持中断或请求取消。

## 四、JVM 与故障排查

### 35. JVM 运行时内存区域有哪些？

**答：**线程私有区域包括程序计数器、Java 虚拟机栈、本地方法栈；线程共享区域包括堆和方法区实现 Metaspace。直接内存不属于堆，但由进程使用，也可能 OOM。对象通常在堆上，局部变量和栈帧在栈中。

### 36. Java 对象是如何创建和分配的？

**答：**检查类是否加载，计算对象大小，在 TLAB 或堆中分配内存，清零，设置对象头，再执行构造器。大多数小对象通过线程本地分配缓冲 TLAB 快速分配；逃逸分析可能进行标量替换和锁消除，但不能假定所有对象都会栈上分配。

### 37. 对象头通常包含什么？

**答：**Mark Word 保存哈希、GC 年龄、锁状态等运行时信息；Klass Pointer 指向类元数据；数组还有长度字段。开启压缩指针会影响引用大小和对象布局，可使用 JOL 查看，不能只凭字段类型简单相加对象大小。

### 38. 类加载过程是什么？

**答：**加载、验证、准备、解析、初始化。准备阶段为静态变量分配内存并设置默认值，初始化阶段执行类构造器 `<clinit>`。类的唯一性由“类加载器 + 全限定名”共同决定。

### 39. 双亲委派模型有什么作用？如何打破？

**答：**类加载请求先委派父加载器，父加载器无法完成再由当前加载器加载，避免核心类被重复或恶意替换。SPI、应用服务器和模块化框架可能通过线程上下文类加载器、子优先策略或自定义 ClassLoader 打破严格委派。

### 40. 哪些对象可以作为 GC Roots？

**答：**活动线程栈中的引用、静态字段引用、JNI 引用、同步锁持有对象、JVM 内部引用等。可达性分析从 GC Roots 遍历，不可达对象才具备回收条件；finalize 已不推荐依赖。

### 41. Young GC、Mixed GC 和 Full GC 有什么区别？

**答：**Young GC 主要回收新生代；G1 的 Mixed GC 会同时回收新生代和部分收益高的老年代 Region；Full GC 通常对整个堆做更重的回收和压缩，停顿明显。不同收集器术语和触发条件不同，排查时应先确认 GC 类型和 JDK 版本。

### 42. 常见垃圾收集器如何选择？

**答：**Parallel GC 重吞吐，适合批处理；G1 兼顾吞吐和可预测停顿，是大堆通用选择；ZGC 追求超低停顿，适合大堆和延迟敏感服务，但要评估吞吐、CPU 和版本成熟度。选择收集器看堆大小、分配速率、停顿目标和资源成本，不是越新越好。

### 43. G1 的核心原理是什么？

**答：**G1 将堆划分为等大小 Region，逻辑上组成 Eden、Survivor、Old 和 Humongous。它通过并发标记估算各 Region 回收收益，优先回收垃圾多的区域，并根据停顿目标选择回收集合。跨 Region 引用由 Remembered Set 辅助追踪。

**追问：**大对象超过一定 Region 比例进入 Humongous Region，过多可能造成碎片和并发周期提前。Mixed GC 回收不等于一次清空老年代。

### 44. ZGC 为什么停顿时间低？

**答：**ZGC 将标记、转移和重映射的大部分工作并发执行，通过染色指针、读屏障等机制让应用线程与 GC 协同，因此停顿通常与堆大小关系较小。代价是额外 CPU、内存和屏障成本。

**追问：**Java 21 提供分代 ZGC。是否启用仍应通过真实负载测试，不能只看宣传停顿数字。

### 45. 什么是 Safepoint 和 Stop-The-World？

**答：**Safepoint 是 JVM 能安全检查线程状态、执行 GC 或偏向撤销等操作的位置。STW 表示应用线程暂停。停顿时间不仅包含 GC 工作，还可能包含线程到达安全点的时间，因此日志中的 Time to Safepoint 也要关注。

### 46. 常见 OOM 类型和排查方法是什么？

**答：**Java heap space 看堆转储和对象占用；Metaspace 看类加载器和动态类数量；Direct buffer memory 看 NIO/Netty 直接内存；unable to create native thread 看线程数、栈大小和系统限制；GC overhead limit 表示大部分时间 GC 却回收很少。

**排查：**先保留现场，收集 heap dump、GC 日志、进程内存、线程和容器限制，再使用 MAT、JProfiler、Arthas 等分析。不要第一反应只加堆。

### 47. Java 进程 CPU 100% 怎么排查？

**答：**先用 top 或监控确定进程和高 CPU 线程，把线程 ID 转为十六进制，再在 jstack 中定位栈；也可使用 Arthas `thread -n`、async-profiler 或 JFR。常见原因包括死循环、自旋、频繁 GC、正则回溯、序列化、大量锁竞争。

### 48. JVM 调优的正确顺序是什么？

**答：**先定义目标并采集基线，再判断问题是分配速率、内存泄漏、堆不足、收集器不匹配还是业务慢。优先优化对象生命周期和业务代码，再调整堆、GC 和线程参数。关注吞吐、P95/P99 停顿、分配速率、晋升速率和 Full GC，而不是只追求“零 Full GC”。

## 五、Spring、Spring Boot 与 MyBatis

### 49. Spring IoC 的核心原理和 Bean 生命周期是什么？

**答：**容器读取 BeanDefinition，实例化对象，填充依赖，执行 Aware、BeanPostProcessor 前置处理、初始化方法和后置处理，最终放入单例池；销毁时调用销毁回调。AOP 代理通常由 BeanPostProcessor 在初始化后创建。

### 50. BeanFactory 和 ApplicationContext 有什么区别？

**答：**BeanFactory 是基础 IoC 容器接口，提供 Bean 创建和获取；ApplicationContext 在其上增加事件、国际化、资源加载、环境、自动注册后处理器等企业能力。实际 Spring Boot 应用使用 ApplicationContext。

### 51. Spring AOP 的执行原理是什么？

**答：**容器根据切点为目标 Bean 创建 JDK 或 CGLIB 代理，调用代理方法时按拦截器链执行通知和目标方法。AOP 适合事务、日志、权限和监控等横切逻辑。

**追问：**private、final、自调用、非容器对象等场景可能绕过代理。AspectJ 编织与 Spring 代理 AOP 的机制不同。

### 52. `@Transactional` 为什么会失效？

**答：**常见原因是同类自调用绕过代理、方法不是可代理的 public 方法、对象不是 Spring Bean、异常被捕获未抛出、抛出 checked exception 但未配置 rollbackFor、数据库引擎不支持事务、异步切换线程。

**追问：**不要为了事务而随意从容器获取自己。可拆分 Bean、注入代理对象或使用 TransactionTemplate；事务边界应短，避免持有连接调用远程服务。

### 53. Spring 事务传播行为怎么理解？

**答：**REQUIRED 加入现有事务或新建；REQUIRES_NEW 挂起外层并新建；NESTED 使用保存点，依赖数据库；SUPPORTS 有则加入；NOT_SUPPORTED 挂起；MANDATORY 要求已有；NEVER 要求没有。

**追问：**REQUIRES_NEW 需要额外连接，高并发下可能耗尽连接池。内外事务异常传播和回滚标记容易导致 UnexpectedRollbackException。

### 54. Spring 事务隔离级别和 MySQL 隔离级别是什么关系？

**答：**Spring 只是通过 JDBC 设置连接隔离级别，真正语义由数据库实现。DEFAULT 使用数据库默认；READ_COMMITTED、REPEATABLE_READ 等映射到 JDBC。连接池复用时框架应在归还前恢复状态。

### 55. Spring 如何解决循环依赖？

**答：**单例 Bean 的 setter/字段循环依赖可通过三级缓存提前暴露对象引用：成品单例、早期单例、单例工厂。构造器循环依赖无法先实例化对象，通常失败。引入代理时三级缓存中的 ObjectFactory 用于提前获得一致代理引用。

**追问：**循环依赖通常说明模块职责不清，能重构就不要依赖容器技巧；Spring Boot 新版本默认策略也可能限制循环引用。

### 56. Spring 单例 Bean 是线程安全的吗？

**答：**单例只表示容器中一个实例，不保证线程安全。无状态 Service 通常安全；把请求参数、可变集合或计数器放在实例字段会发生竞争。共享状态应使用并发结构、原子变量、锁，或移动到数据库/Redis。

### 57. Spring Boot 自动配置原理是什么？

**答：**自动配置类通过 AutoConfiguration.imports 被导入，结合 `@ConditionalOnClass`、`@ConditionalOnMissingBean`、配置属性等条件决定是否生效。用户自定义 Bean 通常可以覆盖默认实现。

**追问：**排查自动配置可查看 ConditionEvaluationReport、启动 debug 日志和 Actuator conditions，不能只猜 Bean 为什么没创建。

### 58. Spring MVC 请求处理链路是什么？

**答：**请求先经过 Filter，再到 DispatcherServlet；它通过 HandlerMapping 找控制器，HandlerAdapter 调用方法，参数解析器和消息转换器完成绑定，返回值处理器序列化响应；异常交给 HandlerExceptionResolver。Interceptor 位于 MVC 调用链内。

### 59. MyBatis 中 `#{}` 和 `${}` 有什么区别？

**答：**`#{}` 使用 PreparedStatement 占位符，可避免 SQL 注入并复用执行计划；`${}` 是字符串直接替换，只能用于经过严格白名单校验的表名、排序字段等结构部分。普通参数禁止使用 `${}`。

### 60. MyBatis 一级缓存和二级缓存有什么问题？

**答：**一级缓存默认是 SqlSession 级，同一会话重复查询可复用，更新或提交会清理。二级缓存是 Mapper namespace 级，需要序列化和失效管理，在分布式、联表和高频更新场景容易产生旧数据，因此很多项目不启用，改用明确的业务缓存。

### 61. MyBatis 如何优化批量写入、分页和 N+1？

**答：**批量写使用批处理 Executor 或合理大小的多值 INSERT，控制单批大小和事务时间；深分页使用游标/主键 seek；N+1 通过 JOIN、批量 IN 查询或预加载解决。IN 列表也要分批，避免 SQL 过长和优化器压力。

## 六、MySQL

### 62. InnoDB 的核心组成是什么？

**答：**磁盘上有表空间、页、索引和日志；内存中核心是 Buffer Pool，缓存数据页和索引页。写入先修改 Buffer Pool 中的页并产生 redo，后台刷脏页。InnoDB 支持事务、行锁、MVCC 和崩溃恢复。

### 63. 为什么 MySQL 索引使用 B+ 树？

**答：**B+ 树分支因子高、树高低，适合磁盘页读取；非叶子节点只保存键和指针，叶子节点保存数据或主键并形成有序链表，因此点查、范围查询和排序都高效。红黑树层级更深，Hash 不支持范围和有序扫描。

### 64. 聚簇索引和二级索引有什么区别？

**答：**InnoDB 聚簇索引叶子节点保存整行数据，一张表只有一个，通常是主键。二级索引叶子节点保存索引列和主键，查询其他列需要根据主键回表。主键过大会膨胀所有二级索引，因此常用短、稳定、递增趋势的主键。

### 65. 什么是覆盖索引和索引下推？

**答：**查询所需字段全部在索引中时无需回表，称覆盖索引。索引条件下推 ICP 让存储引擎在扫描索引时先判断可利用的非首列条件，减少回表。两者都能降低随机 I/O，但要避免为每个查询创建过宽索引。

### 66. 联合索引的最左前缀原则是什么？

**答：**B+ 树按联合索引列顺序排序，查询通常从最左列开始才能持续缩小范围。遇到范围条件后，后续列通常不能继续用于定位，但可能用于 ICP 或覆盖。索引列顺序要综合等值条件、选择性、排序、分组和覆盖需求，而不是只看区分度。

### 67. 哪些情况会导致索引效果差或失效？

**答：**对索引列做函数/计算、隐式类型转换、前导模糊 LIKE、OR 分支无合适索引、联合索引跳过前导列、返回比例过高、统计信息不准。是否使用索引由优化器成本决定，“有索引”不等于一定走。

### 68. Explain 重点看哪些字段？

**答：**type、possible_keys、key、key_len、rows、filtered、Extra。访问类型通常从 const/ref/range 到 index/all 逐渐变差，但要结合扫描行数。Extra 中关注 Using filesort、Using temporary、Using index、Using index condition。

**追问：**Explain 是估算，复杂慢 SQL 还要结合 `EXPLAIN ANALYZE`、实际耗时、锁等待和性能 Schema。

### 69. MVCC 的实现原理是什么？

**答：**InnoDB 通过隐藏事务 ID、回滚指针、undo 版本链和 Read View 实现一致性读。Read View 记录活跃事务范围，查询沿版本链找到当前事务可见版本。MVCC 减少读写阻塞，但旧版本过多会增加 undo 和 purge 压力。

### 70. RC 和 RR 的主要区别是什么？

**答：**RC 通常每次一致性读创建新的 Read View，因此能看到其他事务后续提交；RR 通常在事务第一次一致性读时创建 Read View并复用，保证重复读结果稳定。InnoDB RR 对当前读还通过 Next-Key Lock 防止范围内插入造成幻读。

### 71. 快照读和当前读有什么区别？

**答：**普通 SELECT 通常是快照读，读取 MVCC 可见版本，不加行锁；`SELECT ... FOR UPDATE/SHARE`、UPDATE、DELETE 是当前读，读取最新已提交/可锁定版本并加锁。事务中混用时结果可能不同。

### 72. InnoDB 有哪些锁？

**答：**行级 Record Lock、Gap Lock、Next-Key Lock、意向锁，以及表级元数据锁 MDL。锁最终加在索引记录或间隙上，没有合适索引时可能扫描并锁住大量记录，表现得像锁表。

### 73. Gap Lock 和 Next-Key Lock 解决什么问题？

**答：**Gap Lock 锁索引记录之间的间隙，Next-Key Lock 是记录锁加前面间隙，主要用于 RR 当前读防止其他事务在查询范围插入新记录。唯一索引等值命中通常可退化为记录锁；RC 下大部分 Gap Lock 不使用。

### 74. MySQL 死锁如何产生和排查？

**答：**两个事务以不同顺序持有并等待对方资源形成环路。InnoDB 检测后回滚代价较小的事务。通过 `SHOW ENGINE INNODB STATUS`、performance_schema、慢日志和业务 Trace 查锁对象与 SQL。

**避免：**统一访问顺序、缩短事务、建立合适索引、减少批量锁范围、捕获死锁错误并有限重试。

### 75. redo log、undo log、binlog 分别做什么？

**答：**redo 是 InnoDB 物理/逻辑重做日志，用于崩溃恢复；undo 保存旧版本，用于事务回滚和 MVCC；binlog 是 Server 层逻辑日志，用于复制、审计和恢复。三者职责不能互相替代。

### 76. redo log 和 binlog 为什么需要两阶段提交？

**答：**一次事务同时写 InnoDB redo 和 Server binlog，如果只成功一个会导致主库恢复状态与复制状态不一致。MySQL 先写 redo prepare，再写 binlog，最后 redo commit；恢复时根据 binlog 是否完整决定提交或回滚 prepared 事务。

### 77. MySQL 主从复制流程和延迟原因是什么？

**答：**主库写 binlog，从库 I/O 线程拉取为 relay log，SQL/applier 线程重放。延迟可能来自大事务、从库单线程瓶颈、无主键更新、磁盘/网络慢、锁冲突和从库查询压力。可使用并行复制、拆小事务、优化索引和读写负载。

### 78. 慢 SQL 如何系统排查？

**答：**先确认慢在执行、锁等待、连接池还是网络；查看慢日志、监控和 Trace；用 Explain/Analyze 检查扫描行数、索引、排序、临时表；再评估 SQL 改写、索引、表结构、分区/分片和缓存。优化后要对比执行计划、P95/P99 和资源消耗。

### 79. 深分页如何优化？

**答：**`LIMIT offset,size` 需要扫描并丢弃大量记录。可使用基于唯一有序键的 seek 分页：`WHERE id > lastId ORDER BY id LIMIT n`；复杂排序先用覆盖索引查主键再回表；搜索场景使用 ES search_after/PIT。

### 80. `COUNT(*)` 为什么慢？如何优化？

**答：**InnoDB 不保存精确总行数，需要扫描可见记录或索引。优化包括选择较小索引、限制统计范围、维护异步汇总表或近似统计。高并发下不要每次列表查询都实时全表 count。

### 81. 分库分表需要解决哪些问题？

**答：**除路由算法外，还要解决全局 ID、跨分片查询、分页排序、唯一约束、事务、扩容、数据迁移、归档和监控。分片键应匹配最高频访问路径，并避免热点。任务维度聚合可投影到 ES，单样本查询按 resultDetailId 路由。

## 七、Redis

### 82. Redis 为什么快？

**答：**核心数据在内存中，数据结构经过优化；命令执行主路径串行，避免大量锁；使用 I/O 多路复用处理连接；协议简单。Redis 6 以后可用 I/O 线程处理网络读写，但命令执行仍主要串行，慢命令仍会阻塞其他请求。

### 83. Redis 常用数据结构和典型场景是什么？

**答：**String 用于缓存、计数、分布式锁；Hash 表示对象字段；List 用于简单队列但可靠消息优先 MQ；Set 去重和集合运算；ZSet 排行榜和延迟调度；Bitmap 做签到；HyperLogLog 近似 UV；Stream 做轻量消费组。

### 84. Redis 底层编码为什么会动态变化？

**答：**Redis 根据元素数量和大小在 listpack、hashtable、skiplist 等编码间转换，小数据优先紧凑存储，大数据切换为操作效率更稳定的结构。具体阈值随版本变化，面试应讲设计思想，不死背旧版 ziplist 参数。

### 85. Redis Key 如何过期和淘汰？

**答：**过期删除结合惰性删除和定期采样，避免为每个 Key 建定时器。内存达到 maxmemory 后按策略淘汰，如 allkeys-lru、allkeys-lfu、volatile-ttl、noeviction。近似 LRU/LFU 通过采样实现，不是全局精确排序。

### 86. RDB 和 AOF 如何选择？

**答：**RDB 是时间点快照，文件紧凑、恢复快，但可能丢失最近周期数据；AOF 记录写命令，数据更完整但文件和重写成本更高。常见做法是混合持久化并结合主从、备份和恢复演练。持久化不等于高可用。

### 87. 缓存穿透、击穿、雪崩如何处理？

**答：**穿透是查询不存在数据，可用参数校验、空值缓存、布隆过滤器；击穿是热点 Key 失效瞬间大量回源，可用互斥重建、逻辑过期、热点永不过期；雪崩是大量 Key 同时过期或 Redis 故障，可加随机过期、分批预热、多级缓存、限流降级和高可用。

### 88. 缓存与数据库如何保持一致？

**答：**常用 Cache Aside：读缓存未命中查库并回填；写数据库成功后删除缓存。先更新库再删缓存仍存在短暂窗口，只能提供最终一致。高要求可使用延迟双删、订阅 binlog、消息重试、版本号和过期时间。

**追问：**不要先删缓存再更新库，否则并发读可能回填旧值。缓存更新失败必须可重试和监控。

### 89. Redis 分布式锁的正确实现是什么？

**答：**使用 `SET key uniqueValue NX PX ttl` 原子加锁，释放时 Lua 比较 value 后删除，防止误删他人锁。TTL 防止进程宕机永久占锁，业务执行时间不确定时需要续期。锁只能提供互斥，还要结合数据库状态或版本保证业务幂等。

### 90. 看门狗续期有什么风险？什么是 fencing token？

**答：**续期降低长任务锁过期，但进程长时间 STW、网络分区或 Redis 故障仍可能失锁。旧持锁者恢复后可能继续写。Fencing token 为每次获锁分配单调递增版本，下游只接受更大 token，可阻止过期持锁者写入。

### 91. RedLock 是否能保证强一致分布式锁？

**答：**RedLock 尝试在多个独立 Redis 节点多数加锁，提高单节点故障容忍，但在时钟、网络分区和暂停场景仍有争议。涉及资金等强一致场景更适合数据库唯一约束、ZooKeeper/etcd 租约和 fencing token。不能把 RedLock 描述成绝对安全。

### 92. 热 Key 如何发现和治理？

**答：**通过 Redis hotkeys、代理统计、客户端埋点和监控识别。治理包括本地缓存、Key 分片、读副本、请求合并、限流、预热以及将计算前移。写热点不能简单复制 Key，需要重新设计聚合方式。

### 93. 大 Key 有什么危害？如何处理？

**答：**大 Key 占内存、阻塞序列化和网络、删除时阻塞、迁移和复制缓慢。使用 MEMORY USAGE、bigkeys、扫描工具发现；拆分结构，限制集合长度，使用 UNLINK 异步删除，渐进式迁移。生产扫描使用 SCAN，避免 KEYS。

### 94. Redis 主从复制和 Sentinel 的作用是什么？

**答：**主从复制提供数据副本和读扩展，通常异步，因此故障切换可能丢失少量数据。Sentinel 负责监控、主观/客观下线判断、选主和通知，不做数据分片。脑裂治理需要合理 quorum、故障转移参数和主库最小副本写配置。

### 95. Redis Cluster 的槽位和重定向机制是什么？

**答：**Cluster 将 Key 映射到 16384 个 hash slot，槽分布在多个主节点，客户端根据 MOVED 更新拓扑；迁移期间 ASK 临时重定向。多 Key 操作必须在同一槽，可用 `{tag}` 控制，但过度使用可能形成热点。

### 96. Pipeline、Lua 和事务有什么区别？

**答：**Pipeline 批量发送减少 RTT，但不保证原子；Lua 脚本在 Redis 线程中原子执行，适合短小的读改写；MULTI/EXEC 保证命令顺序执行，但不支持传统回滚，WATCH 可做乐观锁。长 Lua 会阻塞 Redis，必须限制复杂度。

### 97. Redis 故障时如何避免拖垮数据库？

**答：**启用连接和命令超时、熔断、限流、降级和本地缓存；按业务重要性决定 fail-open/fail-closed；恢复时分批预热，避免缓存瞬间回源。数据库侧也要有连接池、慢查询和容量保护，不能假设 Redis 永不故障。

## 八、RocketMQ

### 98. RocketMQ 的核心组件有哪些？

**答：**Producer 发送消息，Consumer 按消费组消费，Broker 存储和投递消息，NameServer 提供轻量路由发现。Topic 划分业务，MessageQueue 是并行消费和顺序性的基本单元；同一消费组中的队列会分配给不同消费者实例。

### 99. RocketMQ 的消息如何存储？

**答：**消息主体顺序写入 CommitLog，ConsumeQueue 保存 Topic/Queue 到 CommitLog 的逻辑索引，IndexFile 支持按 Key 查询。顺序写提高磁盘吞吐，消费通过逻辑队列定位消息，再从 CommitLog 读取。

**追问：**Page Cache、顺序写和零拷贝思路共同提升吞吐；磁盘容量、刷盘策略和消息保留时间仍需治理。

### 100. 如何保证消息可靠发送？

**答：**业务先持久化必要状态，Producer 使用同步发送并检查 SendResult，失败有限重试；Broker 根据可靠性要求选择同步刷盘和主从复制；发送结果未知时不能直接认定失败，应使用业务 Key 查询或依赖幂等重试。

**追问：**只调用一次 send 不等于可靠。数据库更新与发消息之间仍有一致性窗口，可使用事务消息或 Outbox。

### 101. RocketMQ 为什么通常是“至少一次”消费？

**答：**消费者处理成功但提交消费位点前宕机，Broker 会再次投递，所以重复消息不可避免。系统优先保证不丢，再由业务幂等处理重复。所谓 Push Consumer 本质上通常基于客户端长轮询和本地消费线程池。

### 102. 消费幂等如何设计？

**答：**选择稳定业务幂等键，在数据库用唯一约束、状态机或幂等表控制；涉及外部调用时先判断业务状态。Redis SETNX 可做快速拦截，但不能作为唯一事实，过期和故障后仍需数据库兜底。

**项目映射：**以 resultDetailId 加样本锁，并用 `PENDING -> MODEL_RUNNING -> MODEL_CALLED` 条件更新防止重复模型调用。

### 103. 消费失败、重试和死信队列如何处理？

**答：**瞬时异常抛出让 Broker 按退避策略重试，超过最大次数进入死信队列。必须监控重试次数、死信量和最老消息时间，并提供人工查看、修复和重放流程。重放仍要经过幂等校验。

**追问：**业务参数错误、永久性数据缺失不应无限重试；应区分可重试和不可重试异常。

### 104. RocketMQ 如何保证顺序消息？

**答：**全局顺序通常意味着单队列，吞吐很低；业务一般保证同一订单或同一样本局部顺序。Producer 按 sharding key 将相关消息发到同一 MessageQueue，Consumer 对该队列顺序消费。

**追问：**发送重试、消费失败和队列扩缩容都要考虑顺序。能用状态机容忍乱序时，不要为了顺序牺牲吞吐。

### 105. 延迟消息适合什么场景？

**答：**订单超时、重试、定时提醒等。延迟消息不是精确定时器，受 Broker 调度、堆积和故障影响。大规模任意时间任务还要考虑时间轮、持久化调度表和分片扫描；不能把延迟消息当严格准点任务。

### 106. RocketMQ 事务消息的流程是什么？

**答：**先发送 Half Message，Broker 存储但消费者不可见；Producer 执行本地事务后提交或回滚；状态未知时 Broker 回查 Producer，Producer根据本地事务记录返回结果。

**追问：**事务消息解决本地事务与消息发送的一致性，不保证消费者业务成功，消费端仍需幂等、重试和补偿。

### 107. MQ 堆积如何定位和处理？

**答：**先看生产速率、消费速率和最老消息年龄，再定位消费者是 CPU、I/O、数据库、远程服务还是锁等待瓶颈。可扩消费者、增加队列、批量处理、优化慢调用；若下游已满，盲目扩容只会放大故障，应限流或降级。

### 108. Consumer 位点和 Rebalance 有什么风险？

**答：**集群消费时位点由消费组维护。实例增减或队列变化会触发 Rebalance，队列所有权转移期间可能短暂停顿或重复消费。长时间消费任务要合理设置超时，并确保 Rebalance 前后的幂等。

### 109. Tag、Key 和 SQL 属性过滤如何使用？

**答：**Tag 用于 Topic 内简单业务分类；Key 用于消息查询和业务追踪，不等于唯一约束；SQL 属性过滤支持更复杂条件但增加 Broker 过滤成本。Topic 不应无限细分，也不应把完全无关业务都塞进一个 Topic。

### 110. RocketMQ 在哪些环节可能丢消息？

**答：**Producer 未确认发送、Broker 异步刷盘宕机、主从复制窗口、Consumer 先提交位点再处理、业务捕获异常却返回成功，都可能丢。分别通过发送确认、可靠刷盘复制、处理成功后 ACK、异常上抛和业务补偿治理。

### 111. 能实现 Exactly Once 吗？

**答：**端到端严格 Exactly Once 很难，因为消息系统、数据库和外部服务跨多个故障域。工程上通常采用至少一次投递加业务幂等，达到“效果上的一次”。不要把 Broker 的去重能力等同于整个业务正好一次。

## 九、Elasticsearch

### 112. 什么是倒排索引？

**答：**倒排索引从“文档包含哪些词”反转为“词出现在哪些文档”，通常包含词典、倒排表、词频和位置等信息。查询先定位 Term，再获取候选文档，适合全文检索；精确结构化过滤使用 keyword、数值和 Doc Values。

### 113. `text` 和 `keyword` 有什么区别？

**答：**text 会经过分词器生成多个 Term，适合全文检索；keyword 作为整体，适合精确匹配、排序和聚合。同一字段可使用 multi-fields 同时建立 text 与 keyword 子字段。错误 Mapping 上线后通常需要新索引重建。

### 114. Analyzer 的组成和使用原则是什么？

**答：**Analyzer 由 character filter、tokenizer、token filter 组成。索引分析器决定写入 Term，搜索分析器处理查询文本，二者应语义兼容。中文需选择适合业务词库的分词器，并通过 `_analyze` 验证，不能只凭默认配置。

### 115. Primary Shard 和 Replica Shard 有什么作用？

**答：**主分片决定数据水平拆分和写入路由，副本提供高可用和读扩展。主分片数量通常创建索引时确定，副本数可动态调整。分片过多带来堆、文件句柄和协调开销，过少限制并行和单分片容量。

### 116. Elasticsearch 写入流程是什么？

**答：**协调节点根据 `_routing` 定位主分片，将请求发给主分片；主分片校验并写入后复制到副本，再按一致性条件响应。数据先进入内存缓冲和 translog，refresh 后形成可搜索 Segment，flush 后形成持久化提交点并清理部分 translog。

### 117. Elasticsearch 查询流程是什么？

**答：**协调节点将查询广播到相关分片；Query Phase 各分片返回 TopN 文档 ID 和分数，协调节点全局归并；Fetch Phase 再从命中分片获取 `_source`。分片数量和 `from + size` 越大，协调节点内存与网络成本越高。

### 118. refresh、flush 和 merge 有什么区别？

**答：**refresh 将内存缓冲生成新 Segment，使数据近实时可搜索；flush 生成 Lucene commit 并推进 translog；merge 合并小 Segment、清理删除标记，降低查询开销但消耗 I/O 和 CPU。频繁 refresh 会产生大量小 Segment，批量导入时可临时增大 refresh interval。

### 119. Query Context、Filter Context 和 BM25 是什么？

**答：**Query Context 计算相关性分数，Filter Context 只判断匹配，通常可缓存且更快。BM25 根据词频、逆文档频率和文档长度计算相关性，比简单 TF-IDF 更稳定。精确条件放 filter，全文相关性放 query。

### 120. ES 深分页如何处理？

**答：**`from + size` 要在每个分片取更大的 TopN，深分页成本高且受 max_result_window 限制。在线翻页使用 `search_after` 配合稳定唯一排序，要求携带上一页 sort values；遍历一致视图可结合 PIT。Scroll 更适合离线扫描，不适合实时用户分页。

### 121. 聚合查询为什么可能内存高？

**答：**terms 等聚合需要各分片构建桶并在协调节点归并，高基数字段和过大 size 会消耗大量堆。应使用 keyword/数值 Doc Values，限制桶数，使用 composite aggregation 分页，必要时预聚合或建立专用统计索引。

### 122. Bulk 写入如何调优？

**答：**使用 Bulk 降低网络和请求开销，按文档大小和压测选择批次，不是越大越好；控制并发，处理部分失败并按状态码重试。批量导入可调大 refresh interval、临时降低副本，完成后恢复。监控写线程池、拒绝、merge、磁盘和 JVM。

### 123. 如何设计索引生命周期和分片大小？

**答：**按时间或业务维度滚动索引，通过 ILM 管理 rollover、hot/warm/cold 和删除。单分片常以数十 GB 为起点，但没有固定黄金值，要结合文档大小、查询并发、恢复时间和节点规格压测。避免每日小索引产生海量小分片。

### 124. ES 如何做并发更新和幂等写入？

**答：**使用稳定文档 ID，重复 upsert 覆盖同一文档；并发控制使用 `_seq_no` 与 `_primary_term`，或业务版本号/外部版本。脚本更新要防止热点文档和重试冲突。ES 是查询投影时，源数据版本应由 MySQL 决定。

### 125. 向量检索和全文检索如何融合？

**答：**全文检索擅长关键词和精确表达，向量检索擅长语义相似。可分别召回后使用 RRF 融合排名，再用 Rerank 精排；也可按业务权重融合归一化分数。HNSW 是近似最近邻结构，需要权衡召回率、内存、构建和查询参数。

## 十、分布式系统与综合设计

### 126. CAP 和 BASE 如何理解？

**答：**网络分区发生时，分布式系统必须在一致性和可用性之间取舍；CAP 不是平时三选二。BASE 强调基本可用、软状态和最终一致，通过重试、补偿和对账达到业务可接受状态。不同业务可在不同链路选择不同取舍。

### 127. 接口幂等有哪些实现方式？

**答：**天然幂等的 PUT/状态设置；数据库唯一约束；幂等 Token；业务状态机条件更新；消费幂等表；版本号乐观锁。幂等键必须稳定并覆盖正确业务范围，幂等结果还应能返回第一次处理结果。

### 128. 分布式事务有哪些方案？

**答：**XA/2PC 强一致但性能和可用性成本高；TCC 业务侵入大但可控；Saga 适合长事务并依赖补偿；事务消息和 Outbox 适合本地事务加异步事件；Seata AT 适合特定关系库场景。选择取决于一致性要求、参与方和补偿能力。

### 129. Outbox 模式如何解决数据库与 MQ/ES 一致性？

**答：**业务数据和 Outbox 事件在同一本地事务提交，后台调度将事件发送 MQ，消费者回查事实源并幂等写下游，成功后更新事件状态，失败退避重试。还需处理事件积压、重复、乱序、归档和告警。

### 130. 常见限流算法如何选择？

**答：**固定窗口简单但边界突刺；滑动窗口更平滑；令牌桶允许一定突发并限制平均速率；漏桶按固定速率流出；信号量限制在途并发。模型 API 的并发上限适合分布式信号量，QPS/TPM 限制还需令牌桶等速率控制。

### 131. 熔断、降级、隔离和背压有什么区别？

**答：**熔断在下游持续失败时快速拒绝；降级返回简化结果或转人工；隔离用独立线程池、队列、实例限制故障传播；背压让上游感知下游容量并减速。完整稳定性设计通常组合使用，并配合超时、重试预算和监控。

### 132. 如何设计可观测性？

**答：**Metrics 发现趋势和告警，Logs 提供事件细节，Traces 串联跨服务调用。统一 TraceId、业务 ID 和消息 Key；监控 RED/USE 指标、MQ 堆积、线程池、连接池、GC、慢 SQL、Redis/ES 资源。日志应结构化并控制敏感数据和采样。

### 133. 如何做容量评估？

**答：**从业务量拆成每秒请求、每请求读写次数、对象大小和保留周期；计算平均值后引入峰值系数和冗余；分别评估应用 CPU/内存、线程与连接池、数据库 TPS、缓存 QPS、MQ 吞吐、ES 存储和恢复时间。最后通过分层压测验证，不能只靠公式。

### 134. 如何设计高并发异步评测系统？

**答：**任务先持久化并拆为样本，模型调用与安全评测使用独立 Topic；以样本 ID 做状态机和幂等，按模型维度限制并发；结果与节点日志分片存储，ES 做查询投影；中间态通过补偿任务恢复。容量指标看样本吞吐和积压恢复，不只看 HTTP QPS。

### 135. MySQL 到 Elasticsearch 如何处理重复和乱序？

**答：**Outbox 消息只携带事件和聚合 ID，消费者每次回查 MySQL 最新状态，使用稳定 ES 文档 ID 幂等 upsert。旧事件后到时仍写最新快照；更严格场景增加业务版本并使用外部版本控制。失败记录重试次数和下次重试时间。

## 十一、一线大厂场景题

### 场景 1：接口突然从 100ms 上升到 3s，怎么排查？

1. 看监控确认影响范围、时间点和变更。
2. 用 Trace 拆分网关、应用、线程池、数据库、Redis、MQ 和外部调用耗时。
3. 检查 CPU、GC、连接池、线程池队列、锁、慢 SQL、网络和下游错误。
4. 先止损：回滚、限流、降级、扩容或熔断。
5. 保留现场并复盘根因，补监控、容量和回归测试。

### 场景 2：Redis 大面积失效，数据库 CPU 100%，怎么办？

先限流和降级，关闭非核心回源；启用本地缓存或只读兜底；按热点分批恢复缓存，不能全量同时预热；数据库侧限制连接和慢查询。恢复后检查过期是否集中、缓存高可用和演练是否缺失。

### 场景 3：MQ 堆积 1000 万条，怎么恢复？

先停止或限制非必要生产，判断消费者瓶颈；按下游容量临时扩容实例和队列，简化非关键处理，批量消费；持续观察最老消息年龄和失败率。恢复期间避免打垮数据库和 ES，必要时导出消息离线处理。

### 场景 4：MySQL 主从延迟导致用户查不到刚写数据，怎么办？

写后短时间读主库、使用一致性 Token/位点等待、关键查询固定走主库，普通查询接受最终一致；同时排查大事务、无索引更新和从库负载。不能简单让所有读永久走主库。

### 场景 5：ES 数据与 MySQL 不一致，如何修复？

以 MySQL 为事实源，先停止错误增量或修复同步逻辑；按主键范围重建新索引，校验数量、哈希或抽样字段；使用别名原子切换；恢复增量并对账。不要直接在旧索引上边修边提供不可信结果。

## 十二、常见失分点

1. 只背结论，不会解释为什么以及替代方案。
2. 把 volatile 说成能保证 `i++` 原子性。
3. 把 ConcurrentHashMap 说成所有复合操作天然原子。
4. 线程池使用无界队列，却声称 maximumPoolSize 会生效。
5. 把 RR 的所有普通查询都说成加 Gap Lock。
6. 把 Redis 分布式锁说成绝对不会失效。
7. 声称 RocketMQ 或业务链路可以天然 Exactly Once。
8. 把 ES refresh、flush、merge 混为一谈。
9. 所有问题都回答“加缓存、加机器、加索引”。
10. 报 QPS、P95、P99 时不说明统计范围和压测条件。

1. 第一天：Java 集合、JMM、volatile、synchronized、AQS。
2. 第二天：线程池、ThreadLocal、CompletableFuture、死锁与并发场景。
3. 第三天：JVM、GC、OOM、CPU 和内存排查。
4. 第四天：Spring 事务、MyBatis、MySQL 索引、MVCC 和锁。
5. 第五天：Redis 缓存、分布式锁、持久化和集群。
6. 第六天：RocketMQ、Elasticsearch、最终一致性。
7. 第七天：随机抽题模拟，每题先回答 60 秒，再接受 3 分钟追问。
