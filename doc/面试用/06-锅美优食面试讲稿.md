# 锅美优食：项目讲法与高频追问

> 项目定位：第三项目，用来证明电商交易、订单存储、异步编排、缓存和最终一致性方面的经验。
>
> 回答原则：围绕订单主链路展开，不把商品、优惠券、监控、RPA 等所有功能平铺成八个同等重要的亮点。

## 一、项目定位

锅美优食是国美电器旗下的社区食材零售平台，覆盖订单、商品、库存、优惠券和价格等业务。面试时应以订单链路为主线，说明一次下单如何完成前置校验、订单落库、后续状态流转和查询，再补充商品缓存、超时关单和可观测性。

推荐主线：

```text
提交订单
 -> 并行执行独立的只读校验
 -> 串行完成库存、优惠券、订单等有副作用的写操作
 -> 订单按用户维度分片落库
 -> Canal 将订单变更投影到 Elasticsearch
 -> 用户侧按分片键查询，运营侧走 ES 复杂检索
 -> XXL-JOB 扫描并补偿关闭超时订单
```

这条主线覆盖分库分表、并发优化、数据一致性和任务补偿，足以支撑高级 Java 面试追问。

## 二、30 秒项目介绍

我参与的是锅美优食社区食材零售平台，主要涉及订单、商品、库存和优惠券等业务。我负责和参与较多的是订单链路：订单表通过 Sharding-JDBC 按用户维度分库分表，订单号中保留分片路由信息；对下单前彼此独立的只读校验使用 CompletableFuture 并行编排，降低接口串行等待时间；订单数据通过 Canal 从 MySQL 同步到 Elasticsearch，用户交易查询仍以 MySQL 为准，运营筛选和复杂检索由 ES 承担；同时使用 XXL-JOB 对超时未支付订单进行分片扫描和补偿关闭。

## 三、1 分钟标准讲法

锅美优食是一个社区食材零售平台，包含订单、商品、库存、优惠券和价格等模块。我参与的核心是订单相关业务以及部分性能优化。

订单存储方面，随着订单量增长，单表写入和索引维护压力增大，因此使用 Sharding-JDBC 按用户 ID 分片，让用户订单列表查询能够直接路由到固定分片。同时订单号通过雪花算法生成，并保留与用户分片一致的路由信息，使只知道订单号时也可以定位到目标分片。商家或运营侧的多条件查询不适合扫描所有分片，因此通过 Canal 将订单变更同步到 Elasticsearch，ES 用于复杂筛选和分析，MySQL 仍是交易事实数据源。

下单接口方面，基础数据、风控、商品状态和优惠券可用性等没有依赖关系的只读校验原来串行执行，整体耗时会叠加。我们使用专用线程池和 CompletableFuture 并行执行这些校验，统一处理超时和异常；库存扣减、优惠券锁定、订单创建等有副作用的操作仍按业务顺序执行，避免并行写入造成一致性问题。

订单关闭方面，使用 XXL-JOB 对超时未支付订单进行分片扫描，通过状态条件更新避免重复关闭，并将释放库存和返还优惠券设计成可重试操作。项目让我积累了电商交易链路、分库分表、异步编排和最终一致性方面的经验。

## 四、个人职责

推荐回答：

## 五、四个核心亮点

### 1. 订单分库分表与多维查询

订单表按用户 ID 分片，主要原因是用户订单列表和订单详情是高频交易查询，携带用户 ID 时可以单分片路由，避免广播查询。

只使用用户 ID 分片会带来一个问题：部分入口只有订单号，没有用户 ID。解决思路是在雪花订单号中附加或编码与用户 ID 一致的分片基因，解析订单号即可得到路由值。这里的“基因法”不是改变雪花算法的全局唯一性，而是额外保留可计算的分片信息。

不同查询场景应这样分工：

- 用户订单列表：携带用户 ID，路由到单一分片查询 MySQL。
- 订单详情：优先同时携带用户 ID；只有订单号时解析分片基因。
- 运营后台多条件筛选：走 Elasticsearch 查询投影，不实时扫描所有分片。
- 交易状态确认：回查 MySQL，不能把 ES 当作强一致交易数据源。

面试时必须能够说清实际分片键、库表数量和订单号编码方式。如果这些数据记不准确，就讲设计原则，不编造具体分片数量。

### 2. 下单前置校验并行化

下单过程中，部分校验只读取数据且彼此无依赖，例如基础参数、风控结果、商品上下架状态和优惠券可用性。串行执行时总耗时接近各步骤耗时之和，适合使用 CompletableFuture 并行。

正确的边界是：

```text
适合并行：只读、相互独立、失败后无补偿成本的校验
不适合并行：库存扣减、优惠券锁定、订单创建、支付状态修改等有副作用的写操作
```

工程实现需要使用业务专用的有界线程池，而不是直接使用 `ForkJoinPool.commonPool()`；每个任务配置超时和异常转换，主流程统一收集结果。一项关键校验失败时取消或忽略其他结果，并返回明确业务错误。线程池容量应结合下游连接池和接口容量设置，不能只追求并行数量。

当前简历中的“RT 从 260ms 降至 100ms”只有在能说明压测或监控口径时保留。否则改为：

> 使用 CompletableFuture 并行编排相互独立的下单前置校验，缩短串行等待时间，并通过独立线程池、超时和异常处理隔离下游波动。

### 3. MySQL 到 Elasticsearch 的订单查询投影

分库分表适合按分片键完成交易查询，但运营侧通常需要按时间、状态、门店、商品等条件组合筛选。跨分片实时聚合成本高，因此使用 Canal 订阅 MySQL binlog，将订单变更同步到 Elasticsearch。

MySQL 与 ES 的职责应明确：

```text
MySQL：订单事实、事务更新、支付和售后状态确认
Elasticsearch：运营筛选、复杂组合查询、搜索和分析
```

Canal 链路只能提供最终一致性。面试时需要能说明消费端如何按订单 ID 幂等 upsert、如何处理删除和状态更新、ES 不可用时如何重试或补偿，以及出现差异时如何进行全量重建或数据校验。没有实际实现的机制不要说成已经落地。

这个场景适合 Canal，是因为需要把数据库表变更通用投影到查询索引；安全评测平台使用 Outbox，则是因为需要在业务事务中明确控制具有业务含义的同步事件。两者解决的问题相似，但事件来源和控制粒度不同。

### 4. 超时关单的分片扫描与幂等补偿

未支付订单到期后需要关闭并释放相关资源。使用 XXL-JOB 将扫描任务分配到多个执行器，每个分片查询满足“待支付且已超时”的订单，再通过带前置状态的条件更新抢占处理权：

```sql
UPDATE order_info
SET status = 'CLOSED'
WHERE order_id = ?
  AND status = 'PENDING_PAYMENT';
```

只有更新成功的执行器才继续执行库存释放、优惠券返还等后续操作，避免重复任务造成重复关闭。批量扫描需要基于 `status + expire_time` 等实际查询条件设计索引，并限制单批数量，避免一次事务处理过多订单。

如果业务同时使用延迟消息，推荐口径是“延迟消息负责及时触发，XXL-JOB 负责兜底扫描”；如果实际只有 XXL-JOB，就不要虚构延迟队列。

简历中“从 10 单/s 提升到 50 单/s”也必须能够说明任务批次、执行器数量和统计方式，否则改为定性描述。

## 六、辅助亮点

### 1. 优惠券过期状态

通过定时任务批量处理已过期优惠券，同时在用户查询或使用优惠券时校验过期时间并惰性修正状态。定时任务保证大部分数据及时收敛，访问时校验保证即使定时任务延迟也不会使用过期优惠券。

更准确的描述是“定时处理 + 访问时校验”，不要说成 Redis Key 过期机制，除非优惠券状态确实由 Redis 过期事件驱动。

### 2. Redis ZSET 热门商品排行

ZSET 适合按热度分值获取 TopN。面试时需要说明 key 的维度、score 如何计算、销量变化如何更新、榜单多久重建以及缓存失效后如何恢复。它可以作为 Redis 追问案例，但不应压过订单主链路。

### 3. ELK 与 SkyWalking

只说“引入可观测性”价值有限。最好准备一个真实故障案例，说明如何通过 traceId 从网关、订单服务追踪到库存或优惠券服务，再结合日志和数据库监控定位耗时或错误节点。

### 4. RPA 价格监控

RPA 属于业务自动化补充，不是 Java 高级后端的核心亮点。只有确实参与了数据采集、价格规则、调价审批或异常处理时再展开。简历中的“价格竞争力提升 30%、销售额增长 15%”如果没有业务报表和明确归因，应删除，避免把相关性说成因果关系。

## 七、高频追问

### 1. 为什么订单表按用户 ID 分片，而不是订单 ID？

> 分片键应优先匹配最高频的交易查询。用户侧最常见的是按用户查询订单列表，按用户 ID 分片可以让同一用户的订单落在固定分片。订单详情查询通过订单号中的分片基因得到相同路由。运营侧跨用户筛选不走所有分片扫描，而是走 ES 查询投影。

### 2. 用户 ID 分片会不会产生热点？

> 普通用户 ID 经过取模或哈希后通常分布相对均匀，但仍要关注大客户、测试账号或特殊业务账号。分片前应通过历史数据评估分布，避免直接使用具有明显地域或时间聚集特征的值。热点无法通过简单取模解决时，需要单独拆分热点主体或调整路由策略。

### 3. 为什么订单号要加入分片基因？

> 订单号全局唯一只解决“标识订单”，不能解决“不带用户 ID 时如何路由”。加入分片基因后，可以从订单号解析出与用户 ID 相同的路由值，实现订单详情的单分片定位，避免广播查询。

### 4. 分库分表后如何做分页？

> 用户订单列表携带用户 ID，本质上是单分片分页，可以按时间和订单 ID 组合游标分页。运营后台的跨用户分页走 ES。尽量避免对所有分片执行大 offset 查询后再在应用层归并，因为页码越深，扫描和内存成本越高。

### 5. ES 同步有延迟，用户查不到刚创建的订单怎么办？

> 用户创建订单后的交易详情和状态确认直接查询 MySQL，不能依赖 ES。ES 只承担允许短暂延迟的运营查询和复杂筛选。确实需要读己之写时，可以在短时间内根据订单号回查 MySQL，而不是强行要求 ES 与事务库实时强一致。

### 6. CompletableFuture 如何处理超时和异常？

> 每个外部校验任务使用独立业务线程池，设置超时并把技术异常转换为统一业务结果；主流程通过 `allOf` 等待任务完成后汇总。关键校验失败时整体下单失败，但必须区分“明确业务不通过”和“下游超时无法判断”。有副作用的写操作不放入并行校验阶段。

### 7. 为什么不用 RocketMQ 延迟消息关闭订单？

> 如果只有 XXL-JOB，原因可以是当时业务量和时效要求允许分钟级扫描，定时任务实现简单且便于批量补偿。但它的缺点是扫描数据库和关闭时间存在误差。更完善的方案是延迟消息及时触发、定时任务兜底扫描，两条链路都通过订单状态条件更新保证幂等。

### 8. 关闭订单和释放库存如何保证一致性？	

> 先通过订单状态条件更新获得处理权，再调用库存和优惠券释放。跨服务调用不能依赖一个本地事务全部回滚，应通过业务幂等、重试和补偿保证最终一致性。若使用事务消息或本地消息表，应按真实实现说明；没有实际使用时，不要临时套用 Outbox。

### 9. Canal 同步 ES 和 Outbox + MQ 有什么区别？

> Canal 从 binlog 捕获表级变更，业务代码侵入小，适合通用数据投影，但事件语义依赖对表变更的解析。Outbox 在业务事务中显式记录事件，业务语义和发送时机更可控，但需要应用维护事件表和投递流程。订单通用查询投影可以使用 Canal；安全评测结果这类业务事件投影更适合 Outbox。

### 10. 项目中最难的部分是什么？

> 我认为最难的是分库分表后的查询边界和订单状态一致性。分片后不能继续按照单库思维支持任意条件查询，需要明确交易查询走分片键、复杂查询走 ES；订单超时关闭又涉及订单、库存和优惠券多个状态，需要通过条件更新、幂等和补偿保证重复调度不会产生重复操作。
