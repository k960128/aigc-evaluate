# 源启数据治理平台：项目讲法与高频追问

> 项目定位：第二重点项目，用来证明传统 Java 后端、任务调度、数据采集、数据迁移和稳定性治理能力。
>
> 回答原则：只讲自己参与的模块；量化指标必须能说明统计口径和数据来源；没有真实数据时讲问题、方案和结果，不编造 QPS、服务器数量或可用性。

## 一、项目定位

源启是面向企业的数据治理与数据中台平台，覆盖数据源接入、数据采集、元数据建模、数据管理和数据消费等环节。平台需要连接不同类型的数据源，将采集任务统一编排和执行，并保证采集过程可重试、可恢复、可追踪；同时还要处理元模型升级带来的存量数据迁移和新旧结构兼容问题。

这个项目面试时不要讲成一个泛化的“大数据平台”。个人主线应收敛为：

```text
多数据源接入
 -> 采集任务编排
 -> 分片与并发执行
 -> 断点续跑和异常恢复
 -> 元数据落库与管理
 -> 元模型变更和数据迁移
```

## 二、30 秒项目介绍

我参与的是一个企业级数据治理平台，主要解决不同业务系统的数据源接入、元数据采集、统一管理和数据消费问题。我主要负责多数据源采集、任务调度与执行、元模型变更迁移，以及慢 SQL、OOM 等稳定性问题排查。采集侧通过策略模式隔离不同数据源实现，使用 XXL-JOB 进行任务调度，并结合分片执行、线程池和任务状态实现并发采集与异常恢复；元模型升级时采用新旧结构并行、存量迁移、增量同步、旁路校验和灰度切换，降低结构变更对线上业务的影响。

## 三、1 分钟标准讲法

我参与的是源启数据治理平台，它是一个企业级数据治理和数据中台系统，主要覆盖数据源接入、元数据采集、建模、管理和消费等环节。

我负责的核心方向有三个。第一个是多数据源采集。我们通过策略模式抽象统一采集接口，不同数据源分别实现连接校验、元数据读取和数据抽取逻辑，新增数据源时尽量不修改原有主流程。

第二个是采集任务执行。原来的单机定时任务存在单点故障和大任务执行时间长的问题，因此使用 XXL-JOB 统一调度，结合分片广播和受控线程池拆分采集任务。任务执行过程中记录实例状态和处理进度，使失败任务能够从已确认的位置继续处理，而不是每次全量重跑。

第三个是元模型变更。元数据结构升级时，直接修改旧表容易造成长事务、锁表和新旧版本不兼容，因此采用新旧结构并行、存量迁移、增量同步、旁路校验和灰度切换。数据核对通过后再逐步停止旧结构写入，避免一次性切换带来的风险。

此外，我还参与慢 SQL 和 OOM 问题排查。这个项目让我积累了任务调度、多数据源扩展、数据迁移以及 Java 应用稳定性治理方面的经验。

## 四、个人职责

面试时建议这样回答：

> 我的职责主要集中在采集执行链路和元数据变更两部分。采集侧，我参与多数据源采集接口设计，通过策略模式隔离不同数据源实现，并参与 XXL-JOB 调度、任务分片、线程池并发和异常恢复。元数据侧，我参与元模型升级过程中的新旧结构兼容、存量与增量迁移、旁路校验和灰度切换。另外，我处理过慢 SQL 和 OOM 等线上问题。我的工作重点是 Java 后端的采集任务工程化和稳定性，并不是负责整个数据治理产品的全部模块。

不要把“参与技术选型、性能优化及核心模块设计与开发”作为主要职责。这句话过于宽泛，应落到具体模块和具体问题上。

## 五、三个核心亮点

### 1. 可扩展的多数据源采集框架

不同数据源在连接方式、元数据结构、分页能力和类型映射上存在差异。如果在主流程中堆积条件判断，新增数据源会不断修改核心代码。

因此将公共流程和数据源差异拆开：公共流程负责参数校验、任务创建、状态管理、异常记录和结果落库；数据源策略负责连接、元数据读取、分页抽取和类型转换。运行时根据数据源类型选择对应实现，使新增数据源主要增加一个策略实现和配置，而不改动任务主链路。

面试追问时至少要能说明：

- 统一接口中有哪些关键方法。
- 不同数据源的分页、字段类型和驱动如何隔离。
- 数据源连接如何释放，连接超时如何控制。
- 新增一种数据源需要修改哪些代码和配置。

### 2. 可恢复的采集任务执行链路

原有单机定时任务存在单点故障，且大任务串行执行时间长。使用 XXL-JOB 统一调度后，将任务按数据源、数据表或其他稳定维度拆分到不同执行器，再由受控线程池处理分片内部任务。

这里真正的亮点不是“用了 XXL-JOB”，而是执行可靠性：任务实例需要有唯一标识和明确状态；重复调度时要避免同一分片重复写入；失败时要根据已保存进度继续处理；执行器异常后允许其他节点接管未完成任务。

面试中可以用下面的结构回答：

```text
XXL-JOB 负责调度和节点分配
 -> 分片键保证任务可稳定拆分
 -> 有界线程池控制单节点并发
 -> 任务实例记录开始、进度、成功和失败状态
 -> 重试时根据任务状态和进度恢复
 -> 写入侧通过业务唯一键或幂等判断避免重复数据
```

只有在真实实现中保存了主键、水位或 offset 时，才能明确说“断点续跑”。如果只是失败后重新执行当前分片，应表述为“支持分片级重试和异常恢复”。

### 3. 元模型变更下的平滑迁移

元模型升级可能涉及字段结构、关联关系或存储方式变化。直接在旧结构上修改容易造成锁表、长事务和新旧版本兼容问题。

采用类似 Expand and Contract 的迁移过程：

```text
准备新结构
 -> 应用兼容新旧结构
 -> 写入新旧结构或记录增量变更
 -> 分批迁移存量数据
 -> 对数量、关键字段和业务结果做旁路校验
 -> 小范围灰度读取新结构
 -> 全量切换
 -> 观察稳定后下线旧结构
```

这套方案的关键不是“双写”本身，而是如何处理迁移期间的新写入、如何校验新旧数据、如何回滚，以及什么时候允许停止旧链路。

## 六、必须修正的简历表述

### 1. XXL-JOB 与可用性指标

当前简历写了“全年可用性从 99.95% 提升至 99.99%”。只有能够说明监控指标、统计周期、故障次数和计算方式时才能保留。

更稳妥的写法：

> 使用 XXL-JOB 替代单机定时任务，通过多执行器部署、故障转移、失败重试和任务状态记录，降低单节点故障对采集任务的影响。

XXL-JOB 的故障转移只负责选择可用执行器，不自动保证任务幂等，也不能单独证明四个九可用性。

### 2. “自研 ETL”表述

“自研 ETL”容易被追问为什么不用 DataX、Flink 或 SeaTunnel，以及是否支持复杂转换、血缘、脏数据和 Exactly Once。

如果实际功能主要是平台内部的数据采集，建议改成：

> 面向平台采集场景实现任务执行框架，结合 XXL-JOB 分片、受控线程池和任务进度记录，支持大任务并发处理和异常恢复。

### 3. Seata 使用边界

当前简历写“引入 Seata 解决不同元数据表事务一致性”不成立。同一个数据库中的多张表应优先使用本地事务。

只有实际存在跨服务或跨库写入时，才可以说：

> 在跨服务、跨库的元数据变更场景中使用 Seata 协调事务；单库内多表更新仍使用本地事务。

如果没有跨库或跨服务事务，应删除这一条，不要为了技术栈保留 Seata。

### 4. 慢 SQL 和 OOM

“完成慢 SQL 优化及 OOM 问题排查”必须各准备一个真实案例。至少说明：

- 现象和影响范围。
- 使用什么监控、日志、执行计划或堆转储定位。
- 根因是什么。
- 具体修改了什么。
- 如何验证问题已经解决。

在真实案例没有补全前，不要编造索引、堆大小或性能数字。

## 七、高频追问

### 1. 为什么不直接使用 DataX、Flink 或 SeaTunnel？

> 我们实现的不是通用离线计算平台，重点是将平台内部的数据源配置、元数据模型、采集任务状态和权限审计结合起来。现有需求中的转换逻辑相对固定，自有执行框架更容易和平台业务模型整合。如果后续出现大规模实时计算、复杂 DAG 或 Exactly Once 需求，我会优先评估 Flink、SeaTunnel 等成熟引擎，而不是继续扩大自研范围。

### 2. XXL-JOB 分片广播和线程池为什么同时使用？

> 分片广播解决多执行器之间的任务拆分，线程池解决单个执行器内部多个子任务的并发执行。两层并发必须同时受控，不能简单相乘。线程池需要独立配置核心线程数、队列长度和拒绝策略，并结合数据源连接池容量限制并发，避免采集线程把源库或本地连接池打满。

### 3. 如何保证任务不重复执行？

> 调度系统通常是至少一次语义，不能依赖 XXL-JOB 自动去重。业务侧以任务实例、分片和采集对象组成执行唯一标识，执行前检查状态，写入侧再通过业务唯一键、条件更新或幂等表兜底。任务重试时只继续未完成的处理范围。

这段回答必须根据真实实现删减；没有唯一键或幂等表时不要声称已经实现。

### 4. 如何实现断点续跑？

> 核心是保存稳定且单调递增的处理位置，例如主键、时间水位或分页游标。每批数据成功落库后再推进 checkpoint，失败时从最后一次已确认位置继续。对于没有稳定排序键的数据源，需要退化为分片重跑并依赖写入幂等，不能假装可以精确续跑。

### 5. 元模型迁移期间双写失败怎么办？

> 旧结构在切换前仍是可回退的数据基线。新结构写入失败时记录失败范围并重试，迁移任务持续补齐；旁路校验发现差异时暂停灰度扩大。只有增量追平、关键字段校验通过且观察期稳定后，才切换读取流量。方案目标是可回滚和最终收敛，不声称普通双写天然具备强一致性。

### 6. 为什么要使用 Seata？

> 先判断是不是跨服务或跨库。如果只是同库多表，本地事务更简单可靠；只有一个业务操作跨越多个独立资源，且确实需要统一提交或回滚时才考虑 Seata。同时还要考虑事务模式、锁冲突、长事务和性能成本，不能把 Seata 当成默认方案。

### 7. 项目中最难的部分是什么？

> 我认为最难的是采集任务的可恢复性和元模型变更期间的数据兼容。采集任务可能执行时间长、节点可能中途退出，必须通过分片、任务状态、进度记录和写入幂等保证恢复；元模型变更又不能一次性停机切换，需要同时处理存量迁移、增量数据、新旧版本兼容和结果校验。这两类问题都不是单个中间件可以自动解决的，需要把业务状态设计清楚。

## 八、项目规模的回答边界

目前没有经过核实的服务器数量、QPS、采集吞吐和可用性数据时，建议这样回答：

> 这个平台的核心压力不是面向用户接口的高 QPS，而是周期性采集任务集中触发后，对执行器线程池、数据源连接池、数据库写入和任务积压的压力。我当时主要参与的是任务拆分、并发控制和异常恢复，没有负责统一压测和容量报告，所以不编造具体 QPS。容量评估时会重点看单位时间采集记录数、任务完成时长、失败重试量、连接池占用和调度积压。

## 九、记忆提纲

面试时只需记住六个锚点：

1. 企业数据治理全生命周期，但个人主线是采集执行与元模型变更。
2. 策略模式隔离多数据源差异。
3. XXL-JOB 做调度和节点分配，线程池做节点内受控并发。
4. 断点续跑必须有 checkpoint，重复执行必须有业务幂等。
5. 元模型迁移采用并行、迁移、校验、灰度、回退。
6. Seata 只讲跨服务或跨库，量化指标只讲真实数据。
