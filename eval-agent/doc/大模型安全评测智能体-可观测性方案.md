# 大模型安全评测智能体可观测性方案

版本：1.0  
定位：独立的技术与运维设计方案，暂不作为当前智能体业务开发的前置条件。  
适用范围：`eval-agent` 的智能体编排、目标调用、Judge 判定、样本生产、标准评测、回归评测及报告生成。

## 1. 方案定位

可观测性用于回答三个问题：

1. **发生了什么**：哪一个任务、哪一个 Agent、哪一次目标调用产生了什么结果。
2. **为什么发生**：是模型决策、目标响应、Judge 判定、预算限制、网络故障还是数据问题。
3. **是否需要处理**：是否影响评测结论、是否需要人工复核、是否需要重试或告警。

本方案不负责定义红队策略、风险规则或 Agent 的业务职责，只负责记录、关联、查询和展示这些业务执行过程。

当前阶段先完成业务智能体，暂不要求立刻接入完整可观测性平台。智能体开发时只需要避免破坏本方案要求的业务标识和状态边界；待业务稳定后，再按第
12 节分阶段落地。

## 2. 与当前评测业务的关系

当前产品有三类任务：

| 任务   | 可观测性重点                         |
|------|--------------------------------|
| 标准评测 | 用例执行完整性、目标调用结果、Judge 结果、错误和覆盖率 |
| 自动红队 | 规划、攻击、目标反馈、会话上下文、预算消耗、风险发现和复现  |
| 样本生产 | 种子、变异策略、生成调用、质量检查、去重和人工采纳      |

业务对象的关联关系为：

```text
Activity 活动
  └── Task 业务任务
        └── Run 一次运行
              ├── Attempt 攻击尝试或样本生成尝试
              │     └── Session 会话
              │           └── Probe 探测
              │                 └── Observation 目标观察
              │                       └── Assessment 安全判定
              ├── Finding 风险发现
              ├── Candidate 候选样本
              └── Report 报告快照
```

这些是业务对象，不等同于技术上的 Trace、Span 或日志。技术观测数据必须能够引用业务对象，但不能用 Trace 替代业务状态和审计记录。

## 3. 四类观测数据

### 3.1 结构化日志

回答“某个服务在某一时刻输出了什么运行信息”。适合排查异常、调用失败、重试和状态转换。

日志必须是结构化数据，不能只打印一段无法检索的中文字符串。

### 3.2 指标 Metrics

回答“系统整体运行得怎么样”。例如任务成功率、目标调用延迟、Token 消耗、Judge 失败率、队列积压量。

指标用于聚合和告警，不保存完整 Prompt、响应或工具参数。

### 3.3 链路追踪 Traces

回答“一次任务经过了哪些服务和步骤，以及每一步耗时多少”。例如：

```text
run
 └── orchestrator
      ├── planner-agent
      ├── attacker-agent
      ├── target-adapter
      ├── judge-agent
      └── persistence / event-publisher
```

Trace 用于定位链路和耗时，不代表业务结论，也不能代替证据记录。

### 3.4 业务事件与审计记录

事件用于驱动页面实时更新和异步流程；审计记录用于证明谁在什么时候执行了什么业务操作。

例如“任务暂停”既可能产生一个运行事件，也必须产生一条包含操作者、权限和原因的审计记录。事件可以过期，审计记录不能被普通用户覆盖。

## 4. 统一标识与关联规则

以下标识建议贯穿所有日志、指标、Trace、事件和业务表：

| 标识                 | 含义           | 是否可以替代其他标识           |
|--------------------|--------------|----------------------|
| `tenantId`         | 租户或业务空间      | 不可以由请求参数随意指定         |
| `actorId`          | 发起操作的用户或服务身份 | 不等同于 Agent           |
| `activityId`       | 一组相关评测活动     | 不等同于一次运行             |
| `taskId`           | 业务任务         | 一个任务可以有多次运行          |
| `runId`            | 一次具体执行       | 运行重试应产生新的运行或明确的重试编号  |
| `attemptId`        | 一次攻击或生成尝试    | 不等同于一次 HTTP 请求       |
| `sessionId`        | 一次目标会话       | 只在目标支持会话时使用          |
| `probeId`          | 一次逻辑探测       | 可能对应多次物理请求           |
| `executionId`      | 一次物理执行       | 用于关联真实目标调用           |
| `traceId`          | 技术链路标识       | 不代替 `taskId`、`runId` |
| `spanId`           | Trace 中的一个步骤 | 不作为业务主键              |
| `evidenceRef`      | 受权限保护的证据引用   | 不直接暴露原始敏感内容          |
| `authorizationRef` | 本次执行的授权引用    | 不由模型生成               |

最小关联要求：执行阶段必须具备 `tenantId`、`taskId`、`runId`、`traceId`；目标调用阶段还必须具备 `attemptId`、`probeId`、
`executionId`；产生判定时必须关联 `ruleSetVersion` 和 `evidenceRef`。

## 5. 结构化日志方案

### 5.1 通用字段

建议所有服务输出统一格式的 JSON 日志。以下字段含义必须固定：

| 字段                   | 类型       | 含义                                       |
|----------------------|----------|------------------------------------------|
| `timestamp`          | ISO-8601 | 日志产生时间，统一使用 UTC 存储                       |
| `level`              | Enum     | `DEBUG`、`INFO`、`WARN`、`ERROR`            |
| `service`            | String   | 产生日志的服务，如 `eval-agent`                   |
| `component`          | String   | 具体组件，如 `orchestrator`、`target-adapter`   |
| `eventName`          | String   | 稳定的机器可读事件名称                              |
| `message`            | String   | 面向人的简短说明，不作为查询主键                         |
| `tenantId`           | String   | 租户标识，脱敏后记录                               |
| `taskId` / `runId`   | String   | 业务任务和运行标识                                |
| `traceId` / `spanId` | String   | 技术链路标识                                   |
| `status`             | String   | 当前操作状态                                   |
| `durationMs`         | Number   | 操作耗时，适用于结束日志                             |
| `errorCode`          | String   | 稳定的错误编码，可为空                              |
| `errorType`          | String   | 异常类型，可为空                                 |
| `retryable`          | Boolean  | 是否允许重试                                   |
| `dataClass`          | Enum     | 数据敏感级别，如 `PUBLIC`、`INTERNAL`、`SENSITIVE` |
| `schemaVersion`      | String   | 日志结构版本                                   |

示例：

```json
{
  "timestamp": "2026-09-25T08:30:15.231Z",
  "level": "WARN",
  "service": "eval-agent",
  "component": "target-adapter",
  "eventName": "target_execution_unknown",
  "message": "目标调用结果未知，禁止自动重发",
  "tenantId": "tenant-demo",
  "taskId": "task-1001",
  "runId": "run-2001",
  "attemptId": "attempt-3001",
  "probeId": "probe-4001",
  "executionId": "exec-5001",
  "traceId": "trace-6001",
  "status": "UNKNOWN",
  "durationMs": 30000,
  "errorCode": "TARGET_RESULT_UNKNOWN",
  "retryable": false,
  "dataClass": "SENSITIVE",
  "schemaVersion": "1.0"
}
```

### 5.2 必须记录的关键事件

| `eventName`                                              | 触发时机             |
|----------------------------------------------------------|------------------|
| `task_created`                                           | 创建任务草案           |
| `plan_generated`                                         | 规划 Agent 生成结构化计划 |
| `plan_approved`                                          | 计划和授权通过          |
| `run_started`                                            | 一次运行开始           |
| `agent_call_started` / `agent_call_finished`             | Agent 模型调用开始和结束  |
| `target_execution_started` / `target_execution_finished` | 目标调用开始和结束        |
| `target_execution_unknown`                               | 无法确认目标是否执行       |
| `judge_started` / `judge_finished`                       | Judge 判定开始和结束    |
| `budget_reserved` / `budget_settled`                     | 预算预留和结算          |
| `finding_created`                                        | 产生疑似或确认风险发现      |
| `human_review_recorded`                                  | 人工复核、接受风险或重新打开   |
| `run_paused` / `run_resumed` / `run_stopped`             | 运行控制操作           |
| `report_frozen`                                          | 报告上下文冻结          |

### 5.3 日志禁止内容

默认禁止写入：

- 完整系统提示词、用户原始 Prompt 和模型完整响应；
- 模型内部思维链或隐藏推理过程；
- API Key、数据库密码、访问令牌；
- 未脱敏的个人信息、租户数据和业务凭据；
- 只用于指标聚合的高基数字段，例如完整 Prompt 内容。

完整输入、输出和工具轨迹应写入受权限控制的证据存储，并通过 `evidenceRef` 关联。

## 6. 指标方案

指标命名建议使用 `llm_eval_` 前缀，名称稳定后再接入监控平台。

### 6.1 任务与运行指标

| 指标                                | 类型        | 含义                      |
|-----------------------------------|-----------|-------------------------|
| `llm_eval_runs_started_total`     | Counter   | 已启动的运行数                 |
| `llm_eval_runs_completed_total`   | Counter   | 按最终状态统计的运行数             |
| `llm_eval_run_duration_seconds`   | Histogram | 一次运行从启动到结束的耗时           |
| `llm_eval_runs_active`            | Gauge     | 当前运行中的任务数               |
| `llm_eval_runs_unknown_total`     | Counter   | 出现未知执行结果的运行数            |
| `llm_eval_budget_exhausted_total` | Counter   | 因预算耗尽停止的运行数             |
| `llm_eval_queue_wait_seconds`     | Histogram | 任务从受理到 Worker 开始执行的等待时间 |

### 6.2 Agent 与模型指标

| 指标                                     | 类型        | 含义               |
|----------------------------------------|-----------|------------------|
| `llm_eval_agent_calls_total`           | Counter   | 各 Agent 的模型调用数   |
| `llm_eval_agent_call_duration_seconds` | Histogram | Agent 单次模型调用耗时   |
| `llm_eval_agent_call_errors_total`     | Counter   | Agent 调用错误数      |
| `llm_eval_agent_tokens_total`          | Counter   | 输入、输出及总 Token 消耗 |
| `llm_eval_agent_cost_total`            | Counter   | 按统一币种统计的模型费用     |
| `llm_eval_agent_invalid_output_total`  | Counter   | 输出无法通过结构化校验的次数   |
| `llm_eval_agent_retry_total`           | Counter   | Agent 调用重试次数     |

推荐标签：`agent_role`、`model`、`provider`、`operation`、`status`。  
禁止把 `prompt`、`response`、`sessionId` 等高基数或敏感内容作为指标标签。

### 6.3 目标、Judge 与质量指标

| 指标                                      | 类型        | 含义           |
|-----------------------------------------|-----------|--------------|
| `llm_eval_target_calls_total`           | Counter   | 目标实际调用数      |
| `llm_eval_target_call_duration_seconds` | Histogram | 目标调用耗时       |
| `llm_eval_target_call_errors_total`     | Counter   | 目标调用失败数      |
| `llm_eval_target_unknown_total`         | Counter   | 目标执行事实未知数    |
| `llm_eval_judge_calls_total`            | Counter   | Judge 调用数    |
| `llm_eval_judge_failures_total`         | Counter   | Judge 失败数    |
| `llm_eval_assessments_total`            | Counter   | 按判定结果统计的判定数  |
| `llm_eval_evidence_incomplete_total`    | Counter   | 证据不完整的观察数    |
| `llm_eval_findings_confirmed_total`     | Counter   | 人工确认的去重风险发现数 |

`RISK_OBSERVED`、`NO_RISK_OBSERVED`、`INCONCLUSIVE`、`ERROR` 等判定必须分开统计，不能把未知、错误自动算成无风险。

## 7. 链路追踪方案

### 7.1 推荐的 Span 层级

```text
evaluation.run
 ├── evaluation.plan
 ├── agent.planner
 ├── attack.attempt
 │    ├── agent.attacker
 │    ├── target.execution
 │    └── agent.judge
 ├── sample.generation
 │    ├── agent.generator
 │    └── agent.quality_checker
 └── report.build
```

### 7.2 Span 属性

Span 可以记录：`taskId`、`runId`、`attemptId`、`sessionId`、`probeId`、`agentRole`、`targetType`、`model`、`operation`、`status`、
`errorCode`、`durationMs`。

Span 不应记录完整 Prompt、模型响应、工具参数或个人信息。需要查看原文时，记录经过权限控制的 `evidenceRef`，由业务接口按权限读取。

### 7.3 Trace 使用规则

- 一次运行建立一个根 Trace；异步 Worker 通过消息传递上下文继续该 Trace 或建立可关联的子 Trace。
- 目标适配器必须把 `traceId` 和 `executionId` 传给可传递的下游日志或请求头。
- 重试必须记录独立 Span，并增加 `retryAttempt`，不能覆盖第一次调用。
- `UNKNOWN` 结果必须结束当前执行 Span，但不能伪造成功 Span。
- Trace 丢失不应导致业务任务失败；业务状态和证据记录仍以持久化结果为准。

## 8. 业务事件、实时页面与审计

### 8.1 运行事件

运行事件用于前端刷新状态和展示进度，建议包含：

| 字段                 | 含义                 |
|--------------------|--------------------|
| `eventId`          | 事件唯一标识，用于客户端去重     |
| `sequence`         | 单次运行内单调递增序号，用于断线补发 |
| `runId` / `taskId` | 事件所属运行和任务          |
| `eventType`        | 带版本的事件类型           |
| `occurredAt`       | 事件实际发生时间           |
| `subjectRef`       | 事件涉及的业务对象          |
| `payloadRef`       | 较大或敏感内容的受权引用       |
| `schemaVersion`    | 事件结构版本             |

前端应先获取运行状态快照，再按 `sequence` 订阅或补发事件。SSE 断线只影响页面展示，不能影响后台运行。

### 8.2 审计记录

以下动作必须审计：计划批准、任务启动、暂停、恢复、停止、复现、人工确认、接受风险、重新打开问题、候选采纳、报告确认和权限变更。

审计记录至少保存：操作者、租户、动作、目标对象、动作前状态、动作后状态、原因、授权引用、请求标识、时间和结果。普通业务接口不能删除或覆盖审计记录。

## 9. 页面与仪表盘规划

### 9.1 运行详情页

展示：

- 当前状态、停止原因和最后更新时间；
- 任务、运行、Trace 和授权引用；
- 目标调用、Agent 调用、Token、费用和剩余预算；
- 各阶段耗时：排程、攻击、目标调用、Judge、持久化；
- 会话、探测、判定、证据和未知结果；
- 运行事件时间线。

### 9.2 评测运维大盘

展示：

- 活跃任务和队列等待时间；
- 目标调用成功率、延迟、超时和未知结果；
- Agent 调用错误率、结构化输出失败率、Token 和费用；
- Judge 失败率和证据不完整率；
- 各目标、模型、租户和环境的异常分布。

### 9.3 评测质量大盘

展示：

- 风险覆盖率和未覆盖组合；
- 有效发现、复现成功和人工确认情况；
- 无风险、风险、未知、错误的分布；
- 样本质检、去重、退回和采纳比例；
- 不同规则版本、策略版本和目标快照之间的变化。

业务大盘和技术运维大盘分开，避免把“服务正常”误认为“模型安全”，也避免把“发现风险”误认为“系统故障”。

## 10. 告警规则

告警只针对需要处理的异常，不为每个业务失败都发送告警。

| 优先级 | 示例                                | 处理方式           |
|-----|-----------------------------------|----------------|
| P0  | 大量租户数据越权、凭据泄露、审计链路失效              | 立即停止相关执行并通知负责人 |
| P1  | 目标未知结果持续升高、任务重复调用、预算可能失控、事件无法持久化  | 暂停受影响任务，人工确认   |
| P2  | Agent 结构化输出失败率升高、Judge 错误率升高、队列积压 | 运维排查，可降级或限流    |
| P3  | 单个目标延迟升高、低比例重试、单任务失败              | 记录和聚合，按工作时间处理  |

初始告警不直接依据某个固定百分比。正式上线前需要根据历史基线设置阈值，并同时考虑样本量、持续时间和影响租户数。

## 11. 数据安全与保留策略

### 11.1 分级

| 数据               | 建议级别                 | 处理要求              |
|------------------|----------------------|-------------------|
| 指标数值、耗时、状态       | INTERNAL             | 可进入监控系统，避免高基数标签   |
| 任务配置、策略版本、规则版本   | INTERNAL / SENSITIVE | 按租户和角色授权          |
| Prompt、模型响应、工具轨迹 | SENSITIVE            | 脱敏、加密、通过证据引用访问    |
| 凭据、令牌、个人信息       | SECRET               | 不进入普通日志，使用密钥和凭据系统 |

### 11.2 保留

建议至少区分：

- 指标：保留长期聚合数据，原始高分辨率数据按成本滚动；
- Trace：短期保留完整链路，异常 Trace 可延长保留；
- 日志：普通运行日志按环境保留，安全事件和错误日志单独保留；
- 证据和审计：遵循业务、合规和租户要求，报告引用的证据不能在报告有效期内失效。

具体天数需要结合公司的合规要求、存储成本和数据分类另行确定，本方案不预设固定天数。

## 12. 推荐技术路线

当前项目基于 Spring Boot / Spring AI，后续可以采用以下组合，具体版本等智能体业务稳定后再确定：

| 能力       | 推荐方向                              | 作用                   |
|----------|-----------------------------------|----------------------|
| 应用指标     | Spring Boot Actuator + Micrometer | 暴露 JVM、HTTP、业务和模型指标  |
| 链路追踪     | OpenTelemetry                     | 统一 Trace、Span 和上下文传播 |
| 指标存储     | Prometheus 兼容系统                   | 查询指标和触发告警            |
| Trace 存储 | Jaeger、Tempo 或企业统一平台              | 查看 Agent 到目标的调用链     |
| 日志存储     | 企业日志平台或 Loki / Elasticsearch      | 检索结构化日志              |
| 页面实时更新   | SSE 或企业事件平台                       | 推送运行事件，不承担业务持久化      |
| 业务审计     | 现有关系型数据库或审计平台                     | 保存不可覆盖的业务操作记录        |

技术组件不是业务方案的前置依赖。首先需要确定事件、字段、状态和权限，再选择具体平台；否则容易出现监控平台有数据但无法解释评测结果的情况。

## 13. 分阶段落地计划

### O0：设计约束阶段（当前）

- 保留 `taskId`、`runId`、`attemptId`、`probeId`、`executionId`、`traceId` 等字段；
- 不在 Agent 输出中混入无法解释的内部推理内容；
- 区分成功、失败、未知、取消和无风险判定；
- 所有敏感原文通过 `evidenceRef` 设计，不直接写入普通日志；
- 当前 HTML Mock 不作为生产可观测性实现。

### O1：基础运行观测

- 接入结构化日志；
- 记录任务、运行、Agent、目标、Judge 的开始和结束；
- 接入调用次数、耗时、Token、费用、错误和预算指标；
- 页面展示运行事件和预算状态。

验收重点：能够回答“这次运行执行到哪一步、消耗了什么、为什么停止”。

### O2：调用链追踪

- 接入 OpenTelemetry；
- 打通编排器、各 Agent、目标适配器和 Judge 的 Trace；
- 打通异步消息上下文和重试关系；
- 建立敏感字段过滤和采样策略。

验收重点：能够从一个 `runId` 定位到异常步骤和耗时瓶颈。

### O3：运维监控和告警

- 建立运行、Agent、目标、Judge 和队列大盘；
- 配置未知结果、预算异常、队列积压和错误率告警；
- 建立值班处理手册和告警关闭依据。

验收重点：异常发生后能够被发现、定位、处理和复盘。

### O4：质量与审计闭环

- 关联评测结果、发现、复现、回归和报告；
- 建立规则版本、策略版本和目标快照维度；
- 增加证据完整性、覆盖率、Judge 质量和人工复核指标；
- 完成租户隔离、数据保留、导出和审计检查。

验收重点：能够解释一份报告的来源、局限和全部关键操作。

## 14. 后续开发边界

在所有 Agent 业务完成前，不需要实现本方案的全部内容。智能体开发阶段只需遵守以下底线：

1. 每次模型调用、目标调用和判定都可以关联到一个业务运行上下文。
2. 不把模型的自报成功、失败或置信度直接当作系统事实。
3. 不把未知结果、Judge 失败和目标调用失败转换为无风险。
4. 不在普通日志打印敏感 Prompt、完整响应和凭据。
5. 预算、状态、事件和证据分别建模，不能只靠一条日志恢复业务事实。

等智能体业务稳定后，优先从 O1 开始落地，再根据真实运行数据确定 O2～O4 的技术选型和告警阈值。

只演示部分运行状态、预算、事件和证据引用；真实日志、指标、Trace、告警、持久化和权限控制仍需要后续开发与验收。
